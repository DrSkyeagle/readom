# 这台机器的时间花在哪里

本文的数都是在装了本系统开发构建的 PW3 上实测的，不是估算——个别按实测外推的数就地标出"外推"和"尚未重测"；各节标出了测量日期，没有标的是 2026-10-20 量的。写下来是为了下一次不用重新量一遍，也为了把**看起来值得做、量完发现不值得**的几条记在明处。

硬件：一颗 1 GHz Cortex-A9（i.MX6SoloLite，**没有 3D GPU**）、511 MB 可用内存、256 MB zram、1072×1448 的 16 级灰电子墨水屏。

## 一、开机：52 秒，其中 21 秒是一次性的

开发期间 PID 1 自己记的各阶段时间点（这份记录在 v0.1.0 之前已去掉），加上 `logcat -b events` 的 `boot_progress_*`：

| 到这一步 | 秒 | 这一段花了多久 |
|---|---|---|
| PID 1 开始 | 8.4 | 内核 + initramfs |
| FAT 挂上 | 8.6 | |
| 交叉链接检查完 | 9.8 | 1.3 |
| 映射建好、/data 挂上 | 9.8 | |
| **系统镜像校验完** | **30.8** | **20.9**（576 MiB ÷ 27.6 MiB/s；**镜像 2026-11-02 改成 512 MiB 之后这一项应为约 18.6 秒，尚未重测**） |
| system 挂上 | 30.8 | |
| zygote 起 | 33.4 | 2.6（init 起服务、装触摸模块 0.9） |
| zygote 开始预加载 | 40.2 | **6.8**（ART 起来、读启动镜像 63.7 MB） |
| 预加载完 | 43.6 | 3.4（4715 个类 2.2 秒、资源 0.36 秒） |
| system_server 跑起来 | 44.1 | |
| **屏幕交给使用者** | **52.0** | 7.9 |

**那 20.9 秒只在换过镜像的第一次开机出现**（`SystemStamp.h` 的记录命中之后就跳过），所以常态开机估计约 31 秒（按 52 − 20.9 算，尚未单独实测，见第九节）。

**这 20.9 秒其实是重复劳动**：安装器写完镜像就已经绕过宿主缓存读回来、按发行清单的 SHA256 核对过一遍了。PID 1 不能信它，是因为记录（`/data/pw3/system-verified`）在 ext4 上，而原厂内核没有 EXT4 驱动、安装器写不了。

### 量完发现不值得做：让安装器留一张"我核对过"的条子（2026-10-21 定）

想法是：安装器在 FAT 上留一张条子（大小、mtime、SHA256），PID 1 在 `/data` 没有可用记录时核对文件身份与条子，对得上就跳过 512 MiB 的全读。**不做。** 三条，按重要性排：

**一、收益只有一次升级的 7%。** 这 20.9 秒不在常态开机里，只在换过镜像的那一次开机出现，而那一次紧跟在一次**实测约 5 分钟**的"只换系统"升级之后（`docs/install.md`，2026-10-19 在设备上按日志文件夹的时间算）；完整安装约 18 分钟。省掉它，使用者感知到的是 5 分 21 秒变成 5 分钟。

**二、绑定会比今天弱，而且弱在要紧的地方。** 安装器拿不到 PID 1 用的那份 extent 清单：`install.c` 只算簇的**数量**（`clusters()`，为了查空间够不够），不用 `FIBMAP`／`FIEMAP`。所以条子只能带大小、mtime 和哈希，而**系统镜像的大小是固定的 512 MiB**，大小区分不了两个不同的镜像，能区分的只剩 FAT 那个 2 秒分辨率的 mtime。后果是具体的：有人在安装器跑完之后把 `android/system.img` 换成另一个同样大小的镜像，条子里的哈希仍是安装器验过的那个、与本次配置期望的哈希相等，身份核对也过——**PID 1 会把它挂上去**。今天的全读会当场拒绝。

要补回这个强度，就得让安装器自己算一遍 FAT extent（`FIBMAP`，而且要和 `TestFileMapper.h` 的算法逐段一致）。那不是"多写一个文件"，是把 PID 1 那套映射逻辑在原厂侧再实现一遍并保持两边同步——为 20.9 秒做这个，不划算。

**三、还要加一次开机的暴露窗口。** 安装器校验之后、首次启动之前镜像被就地损坏（大小、mtime 都没变）：今天会被抓住（没有记录 → 全读 → 哈希不符 → 拒绝）；采信条子之后抓不住，要等后台 `pw3-system-verify` 复核，也就是"这一次跑了，下一次才拒绝"。这与记录本身的暴露面同类（`SystemStamp.h` 第 14–23 行写明了），但是**多了一次**。

## 三、量完发现不值得做的：窗口改成 RGB_565

`dumpsys SurfaceFlinger` 的缓冲区清单：**39.7 MB，每一个都是每像素 4 字节**（RGBx/RGBA_8888），而这块屏只有 16 级灰。看上去是白送的一半。

算下来不是：

- **合成本来就不是瓶颈。** 一次翻页里，合成 10.6 ms、送屏 3.6 ms，而**面板自己走一次 GL16 要几百毫秒**。把合成减半，省的是一次翻页的 1%。
- **而且未必更快。** `LumaCompose` 的 8888 有自己的路径，565 走的是"一个像素一个像素转成 32 位"的通用路径（`LumaCompose.h` 写明了）。要快还得先给 565 写一条专门的路径。
- 省下来的内存是实的（约 20 MB），但要动的是 SurfaceFlinger 解析 `PIXEL_FORMAT_OPAQUE` 的地方加上合成器的新路径，**为 4% 的内存动两处核心代码**，不划算。

判断方法：**先看那一项占整件事的几分之几，再决定动不动它。**

另外，这台机器**已经在用软件 Canvas**（`ro.pw3.software_canvas=true`，`ActivityThread` 里的产品策略），不是 HWUI+SwiftShader。没有 GPU 的机器上这条路是对的。

## 四、装一个应用时全编译：22 分 29 秒

现在的做法：安装用 AOSP 默认的 `quicken`（不生成机器码，微信读书编译约 2 分钟，见第六节末），之后由后台编译任务在设备空闲时编到 `speed`（第十二节）。本节记的是安装时全编译的代价，也就是不在安装时全编译的原因。

开发期间安装时曾用 `speed` 全编译。微信读书 2.1.2，APK 127.5 MB、13 个 dex、70.4 MB 字节码：

```
+0:00   下载完
+0:42   dex2oat 开始（--compiler-filter=speed）
+23:11  dex2oat took 1349.213s (1213.043s cpu) (threads: 1)
产物：base.odex 108.3 MB + base.vdex 70.7 MB；整个应用占 349 MB
```

期间 `MemFree` 掉到 **6 MB**，100 MB 被压进 zram，整台机器卡到没法用。

**卡的原因不是 CPU 优先级**：开机之后 installd 本来就把 dex2oat 放进后台调度组（`SetDex2OatScheduling(boot_complete)`，那次安装时的标记就是 `boot_complete`）。卡的原因是内存：

```
dalvik.vm.dex2oat-Xmx = 512m     ← 这台机器一共 511 MB
实测 dex2oat RSS 241 MB
```

**这个 512m 是 AOSP 给手机的默认值**（`build/make/target/product/runtime_libart.mk`），Android Go 的配置也没有改它，本项目也没有改。编译器被允许申请比整台机器还多的内存，于是别的进程全被换出去。**这是明确的错配，不是取舍**——但换成多少要实测，因为 `ro.config.low_ram=true` 已经让 dex2oat 用上了交换文件，上限压太低会把换页从内存挪到 /data 上。

**而贵的不是编译本身，是编了用不到的那 95%**：同一个应用，有使用画像时 **181 秒**编完（不是 1410 秒），产物 75 MB（不是 168 MB）。但**第一次安装没有画像可用**。

当初在安装时全编译，依据是 2026-10-13 的一次测量：不编译时微信读书要 129 秒才到书架，还弹"无响应"。这个数后来不复现（第六节）。

### 这件事的解空间（2026-10-20）

把 70 MB 字节码变成机器码，在这颗核上就是约 1350 CPU 秒。**出路只有三种**：少做一点、换个机器做、换个时候做。

| | 做法 | 这台机器上成不成 |
|---|---|---|
| **少做一点** | 按使用画像只编热方法：**181 秒**，产物 75 MB | **第一次装没有画像**。Android P 的 `.dm`（随 APK 带一份画像）在 8.1 里**完全不存在**——`installd` 和 `PackageManagerService` 里一处 `dex_metadata` 都没有（2026-10-20 查过）。自己实现要改框架，而且画像和 APK 的 dex 校验和绑死，腾讯一更新就失配、退回"编不出东西" |
| **换个机器做** | 在构建机上编好 odex 随镜像发 | 技术上可行（启动镜像和 APK 都是已知的），但 odex 是从别人的 dex 推导出来的，**发出去就是再分发腾讯的软件**，和内置 APK 同一个问题 |
| **换个时候做** | ①装完就能开，慢，后台补编（AOSP 的做法）②把等待放到使用者本来就在等的地方（装完系统的首次启动，有进度画面） | **现在用的是①**：安装用 `quicken`，设备空闲时后台编到 `speed`（第十二节）。当初担心的"不编译时打开要 129 秒还弹无响应"不复现（第六节）。②总时间一样，只是集中在一次等待里 |

还有一条与应用大小有关的事实：**代价按字节码大小成比例**，约 3.1 MB/分钟。微信读书 70 MB 是极端值；一个 5 MB 字节码的普通应用约 1.5 分钟。

## 五、在这台机器上量冷启动，要先绕开的几个坑

都是 2026-10-20 至 10-27 测量时遇到的：

1. **屏幕得是亮的，而且得按住不让它灭。** 灭屏时框架在应用 resume 之后立刻把它停掉（事件日志里是 `am_on_stop_called: …,sleeping`），窗口永远画不出来。`input keyevent KEYCODE_HOME` 不唤醒设备，要 `KEYCODE_WAKEUP` 加 `svc power stayon true`。`am start` 和 `input` 都不重置灭屏计时，所以每一组计时之前都要读一次 `dumpsys power | grep mWakefulness=`：2026-10-27 有一组数就是屏幕睡着时量的，应用起来了但没有前台 Activity，一次冷启动只花 10.9 秒 CPU、22 秒安静，看着像快了五倍，整组作废。
2. **框架自己的 `am_activity_launch_time` 对这个应用不能用。** 微信读书的第一个 Activity（`LauncherActivity`）是个转发壳，在绘制之前就 finish 了，启动过渡被取消，这个数根本不记；而它转到的 `WeReadFragmentActivity` 记出来的是"进程已经起来之后"的时间。开发期间据此读出过"首帧 16.8 秒"，真实冷启动是它的两倍。
3. **主日志环只有 256 KB**（`logcat -g`），微信读书不到一分钟就能把它冲满，事后什么都读不回来。
4. **每一次启动前都要清页缓存，不能只清第一次。** 一块里连测三次，时间会一路往下掉，而且**对 `speed` 掉得比对 `quicken` 多**——`speed` 要读进 105 MB 的 odex，`quicken` 只有 1 MB，所以"热"的那几次系统性地偏袒 `speed`。
5. **同一个应用，数据不同就是两个工作量。** 微信读书登录、书架上有书之后（几百 MB 数据、要同步）冷启动 22–41 秒，数据清空之后同样是 `speed` 编译，只要 **10.6 / 9.7 / 9.5 秒**。量"安装之后第一次打开"和量"天天在用的那次打开"，必须分开说，不能混着算均值。
6. **测量本身别在设备上周期性起进程。** 在这颗单核上，每次采样都起一个进程的脚本自己就要占 6%–22% 的 CPU，比被测的东西还多。只在前后各取一次快照，期间最多留一条常驻的流（比如一条 `adb logcat`）。

可靠的判据是窗口管理器自己说这个包的窗口画完了：

```sh
dumpsys window windows | grep -A3 'weread.eink/com' | grep -c HAS_DRAWN
```

（模式里不能写 `Window{`，设备上这个 grep 把花括号当成区间表达式，一条都匹配不上。）

### 清空应用数据来测首次运行，怎么把数据原样还回去

`pm clear` 之后 uid 不变，所以备份只要在设备上打 tar（`cd /data/data && tar -cf … com.tencent.weread.eink`）、拉回电脑，恢复时解包、`chown -R <uid>:<uid>`、`restorecon -R` 就够了。（换一个系统用户来测全新数据、不碰原有数据，这条路走不通：`config_multiuserMaximumUsers` 是 1。）

**但一定要把 `*-shm` 删掉再启动。** `-shm` 是 SQLite WAL 的共享内存索引；把一份陈旧的 `-shm` 和 `-wal` 一起放回去，SQLite 会忽略 WAL 里的内容。微信读书的登录状态就记在一个 WAL 文件里：连 `-shm` 一起放回去，应用认不出会话、当场把 WAL 截断，登录态就丢了；删掉 `-shm` 再恢复，数据才会原样回来。

```sh
find com.tencent.weread.eink -name '*-shm' -delete
```

### 要重新攒使用画像，只能清空画像文件，不能删掉它

`/data/misc/profiles/{cur/0,ref}/<包名>/primary.prof` 是 installd 在安装时建的，属主和安全标签应用自己造不出来（`cur` 是应用自己的 uid，`ref` 是它的 shared app uid，两个都是 `u:object_r:user_profile_data_file:s0`）。**把文件 `rm` 掉，ART 的画像保存器就没地方写了**——2026-10-20 这么干过一次，应用完整跑了三遍，画像仍然是空的，于是 `speed-profile` 拿着空画像编出 1 MB 的 odex，那一组测量作废，而且过程里没有任何报错。

要重来就清空：

```sh
: > /data/misc/profiles/cur/0/<包名>/primary.prof
: > /data/misc/profiles/ref/<包名>/primary.prof
```

万一已经删了，照着同一台机器上别的应用补回来（属主 `u0_aNN` / `u0_a4NNNN`，模式 600，`chcon u:object_r:user_profile_data_file:s0`）。

## 六、全编译到底买到了什么（2026-10-20 晚实测）

量法：三种编译级别的产物**全部预先编好存起来**，循环里只做"原样放回"，不做编译；顺序 ABBA 交替；每一次启动前都清页缓存。同一份用户数据，六轮，冷启动到书架。

| 轮 | 先测 | `speed` | `quicken` | 差 |
|---|---|---|---|---|
| 1 | speed | 35.4 | 39.9 | +4.5 |
| 2 | quicken | 34.0 | 43.3 | +9.3 |
| 3 | speed | 36.2 | 40.4 | +4.2 |
| 4 | quicken | 41.2 | 40.0 | **−1.2** |
| 5 | speed | 37.9 | 40.1 | +2.2 |
| 6 | quicken | 37.8 | 42.0 | +4.2 |
| **均值** | | **37.1 秒** | **41.0 秒** | **+3.9 秒** |

差值标准差 3.4 秒、标准误 1.4，**t = 2.77（自由度 5）、p = 0.04、95% 区间 [0.3, 7.5] 秒**。两种顺序各三轮，样本均值接近（speed 先 +3.6，quicken 先 +4.1）——三轮一组还不足以证明顺序效应可忽略，只能说这次没看出来。

常驻内存 `speed` 206.9 MB、`quicken` 183.6 MB；产物 176 MB 对 76 MB；编译 1214 秒对 60–93 秒。

另一组 `speed` 对 `speed-profile` 的六轮配对，条件相同、在另一个时间测：34.7 对 36.6 秒，差 +2.0 秒，标准差 4.0，t = 1.22，p = 0.28，95% 区间 [−2.1, 6.1] 秒，六轮里两轮为负；常驻内存 210.6 对 181.1 MB；编译 1214 秒对 159 秒，产物 176 对 78 MB。两组各有各的基线，不能放进同一张表，也不能相减得出 `quicken` 对 `speed-profile` 的差。

所以，**对一次登录前、书架空的冷启动**，全编译买到的是几秒钟，而且不确定度几乎和它一样大；代价是二十分钟、100 MB 盘、23 MB 内存。按一次完整使用（加载书架、开一本书）来量，结论相反：全编译把时间减掉近一半（第十二节）。

两边的 JIT 代码都只有几十 KB（`quicken` 60–132 KB，`speed` 32–44 KB）。**这是体积，不是执行时间**——少量热代码也可以跑很多次，所以它只能说明"JIT 没有被迫大规模补编译"，不能据此断定这几秒全部来自有没有机器码。

### 两种看起来对、其实有偏差的测法

**一块里只在第一次清页缓存。** 放回 `speed` 连测三次、编 `quicken` 连测三次，两轮，得到 `speed` 29.6 秒、`quicken` 35.5 秒，两组标准差都是 7 秒上下、区间大幅重叠。后面两次吃着热缓存，而热缓存对 `speed` 帮助更大（105 MB odex 对 1 MB）：`speed` 三块全是一路降（40.8→21.9→18.0），`quicken` 一升一降。等于系统性地给 `speed` 加分，又把两组方差撑大。

**在循环里编译。** 改成同一轮内配对、每次清页缓存，得到 **+9.9 秒、五轮全部同向、t≈12**，看着非常可信。但每一轮都是"放回 speed 测 → 编 quicken 测"，**quicken 那次永远紧跟在一次把单核占满八十多秒的 dex2oat 之后**，zram 和空闲内存都还没恢复；而 speed 那次只跟在一次文件复制之后。清页缓存清不掉这些。把编译移出循环、顺序交替之后，同一台机器、同一份数据、同一周，差值从 +9.9 掉到 +3.9，标准差从 1.9 涨到 3.4。

**教训**：配对能吃掉"轮与轮之间"的变化，吃不掉"同一轮内两次测量所处环境不同"。只要某个条件总是出现在其中一侧，配对就会把它的影响原封不动地算进差值里，而且因为方差变小，看起来还更显著。

### 第四节那个 129 秒为什么不复现

那是 2026-10-13 的测量，安装时全编译的决定就建立在这个数上。现在不编译时约 41 秒到书架、没有弹窗；2026-10-23 的安装路径实测里三次打开都没有 `am_anr`，最慢 26.7 秒（本节末）。

最可能的解释是此后调过 Java 堆的余量（`heapminfree` / `heapmaxfree` / `foreground-heap-growth-multiplier`，见 `pw3.mk`）：在那之前微信读书 12 MB 存活堆每 0.4 秒回收一次、每次 0.2–0.45 秒，129 秒里多半是垃圾回收，不是解释执行。但这是推断，不是测量：没有人在新的堆参数下单独复现过当时的编译设置。

### 还有一样东西只有按画像编才有：应用镜像

AOSP 的 installd 写得很直白（`frameworks/native/cmds/installd/dexopt.cpp`，`maybe_open_app_image`）：

```c
// Use app images only if it is enabled (by a set image format) and we are compiling
// profile-guided (so the app image doesn't conservatively contain all classes).
if (!profile_guided) { unlink(image_path.c_str()); return Dex2oatFileWrapper(); }
```

设备上 `dalvik.vm.appimageformat=lz4` 是开着的，所以**微信读书没有 `base.art` 的唯一原因就是没有按画像编**。本机给装进来的应用用的编译级别——安装 `quicken`、后台编译 `speed`、被别的应用加载的代码 `speed`——都不按画像编，所以这些应用都没有应用镜像。

**但这一项本身不值钱，已经量过了**：2026-10-16 轮流各三次，有应用镜像 17.6 / 17.2 / 18.4 秒，没有 18.5 / 18.0 / 17.8 秒，**均值差约 0.4 秒，在波动之内**（`docs/design/app-install.md`）。所以"按画像编"的好处在编译时间和占盘上，不在应用镜像上。

### 使用画像是私有设备数据

`profman --dump-classes-and-methods` 能把一份画像还原成**精确到方法签名**的清单（`HPLandroidx/compose/material/IconKt;->Icon-ww6aTOc(…)`，H=热、S=启动、P=启动后）。也就是说一份真实画像就是"这台机器的使用者执行过哪些方法"，能反推用过哪些功能。它还和 APK 的 dex 校验和绑死，换个版本就失配。

**所以画像和波形、校准、adb 密钥同一类：不进包、不进日志、不发给任何人。** 任何"随系统发一份画像"的方案都不成立，画像只能在使用者自己的机器上、从使用者自己的运行里长出来。

### 数据全新时的那一组（当晚补测，每次都清页缓存）

上面六组测的全是一个**老安装**。把数据清空（`pm clear`，连画像一起删）之后重测：

| | 编译耗时 | 冷启动三次 |
|---|---|---|
| `speed` 全编 | 1219 秒 | **10.6 / 9.7 / 9.5 秒** |
| `quicken` 不编 | — | 当晚没测成，见下；2026-10-23 补上（本节末） |

波动几乎消失（三次差 1.1 秒），因为每次都清了页缓存、而且没有一书架书要加载。**所以"微信读书冷启动三十多秒"这句话只对一个用了一阵子的账号成立；刚装好时是十秒。**

`quicken` 那一组当晚没拿到：跑到一半 `system_server` 陷入 `UsageStatsService` 的自激循环（下一小节），占住整颗核，dex2oat 只剩 0.36%，连 `pm clear` 都排不进 binder 队列。

### 测量中撞到的一个缺陷：UsageStatsService 自激

反复清数据、强停、启动超时之后，`system_server` 连续三十多分钟占满单核，线程栈指向 `UsageStatsService.onStatsReloaded → postOneTimeCheckIdleStates`，日志里 `Time changed in UsageStats by +2/+3/+4/-3 seconds` 和 `Flushing usage stats to disk` 一直在刷。

不是时钟走速的问题：屏幕亮着时连量两次 90 秒，墙上与单调时钟只差 ±0.07%。原因在判定方法：`UsageStatsService` 在相邻两条语句里分别读墙上时钟和 `elapsedRealtime`，两者偏离超过 2 秒就判定"时间变了"，重新加载整份使用统计、再排一次空闲状态检查。单核被 dex2oat 占满时，线程在两次读之间被调度出去几秒，这个间隙就被读成了改时；重新加载又耗 CPU，让间隙更大。补丁 0050 改成读出不确定区间，只在整个区间都越过 2 秒时才判定；装上之后的验证里，日志中没有再出现 `Time changed in UsageStats`。回路的分析和守卫见 `docs/known-issues.md`"UsageStatsService 可以自激成满核空转"一节。

### 安装路径和数据全新时的 `quicken` 冷启动（2026-10-23）

安装器自己把微信读书装了一整程（下载 → PackageInstaller → 首次打开），数都来自设备自己的事件日志（`logcat -b events`，不是手表）：

| 步骤 | 从安装任务启动算起 | 用了多久 |
|---|---|---|
| 安装任务启动（开机后 11 秒） | 0:00 | |
| 下载 + 写入会话 | 0:03 → 1:43 | 约 100 秒 |
| `dex2oat took 124.717s (100.492s cpu) (threads: 1)` | 1:43 → 3:47 | **124.7 秒** |
| 安装完成（`firstInstallTime`） | 3:47 | |
| 首页那一格交接给微信读书 | 3:48 | |

对照第四节那一程（同一个 127.5 MB 的包、同一台机器，`speed`）：编译 1349 秒、整程二十多分钟。**`quicken` 把编译从 22 分 29 秒降到 2 分 5 秒。**

冷启动要分三次说，因为**第一次打开和第三次打开差四倍**（同一个安装、同一份全新数据，`am_activity_launch_time` 的 `totalTime`）：

| 第几次打开 | 这个活动自己 | 整程到第一帧 |

| 第一次（装完之后从没打开过） | 22.1 秒 | **26.7 秒** |

## 七、镜像里能去掉什么：量过的 56.3 MB，和它卡在哪（2026-10-21）

第二节那张表是**常驻内存**。这一节是**镜像体积**，数字来自一版开发构建导出镜像的文件清单（`tools/inspect-system-image.py`，普通文件 478.5 MB、1346 个）：

### 卡在哪：AOSP 8.1 没有「从 PRODUCT_PACKAGES 移除」

查过的事实：

- `LOCAL_OVERRIDES_PACKAGES` 只在 `build/make/core/package_internal.mk` 和 `prebuilt_internal.mk` 里接了线，**对 `BUILD_EXECUTABLE` 和共享库无效**。所以 APK（`TelephonyProvider`、`Dialer`、`Mms`）能用受支持的机制顶掉，而 `cameraserver`、`drmserver`、`libstagefright_soft_*`、`libLLVM.so` 不能。
- 它们来自 `pw3.mk` 继承的 `core_base.mk` → `core_minimal.mk` → `base.mk`，三个文件合计约 236 个包。
- **盖掉 rc 文件或造同名空模块是临时方案，不做。** 正确做法是不继承 `core_base.mk`，自己列这台机器需要什么——那是一次结构性改动，验证办法是比对 `installed-files.txt` 的前后差集，看走掉的到底是哪些。

### 字体那一块不一样：机制我们已经控制

AOSP 用 `external/noto-fonts/fonts.mk` 装全部 Noto 字体，那个文件只是一串 `PRODUCT_PACKAGES`。`pw3.mk` 不继承它，在文件开头自己列出要装的字体。这是受支持的做法，不动继承链。

风险查过了：`fonts.xml` 里列了而文件不在时，`Typeface.java` 把该字体族当系统错误并 `return null`（第 913 行），而建回退族的循环 `if (fontFamily == null) continue`（第 960 行）——**回退族被跳过，不是致命错误**。默认族是 Roboto，保留。所以后果是显示方框，不是起不来。做干净还要一起裁 `fonts.xml`，否则每次开机 171 条错误日志、171 次去 mmap 不存在的文件。

#### 裁 `fonts.xml` 这一半另有一个坑，比上面那个更隐蔽（2026-10-21 实测）

包列表能自己列，**`fonts.xml` 本身却顶不掉**，而且顶不掉的方式是不报错：

- `LOCAL_OVERRIDES_PACKAGES` 在 `prebuilt_internal.mk` 第 250 行被包在 `ifeq ($(LOCAL_MODULE_CLASS),APPS)` 里，对 `ETC` 预编译件**完全不读**；`LOCAL_OVERRIDES_MODULES` 在 `base_rules.mk` 第 246–256 行只认 `EXECUTABLES`，别的类别直接 `pretty-error`。
- 两个模块装到同一个路径**也不冲突**：kati 把两条 `copy-one-file` 规则合并成**一条** build 语句，两个中间件都成了它的前置，而配方保留第一条——AOSP 那条。
- 所以按这个办法构建出来的镜像是：**AOSP 的 116 个 family 配 37 个字体文件**，fonts.xml 点名 136 个不存在的文件，构建全程不出一声。去掉继承也没用，因为那条拷贝规则是无条件生成的，与模块在不在产品列表里无关。

受支持的做法是让**同一个模块**去拷不同的文件。AOSP 自己已有 `ADDITIONAL_FONTS_FILE`（往 fonts.xml 里加 family），补丁 0052 照同样形状加 `REPLACEMENT_FONTS_FILE`（换掉整份），设备在 `BoardConfig.mk` 里指过去。一个模块守住一个路径。

这个坑是测试抓到的，不是靠看出来的：`tools/tests/test_font_config.py` 里有一条「暂存目录里的 `/system/etc/fonts.xml` 必须和仓库里那份逐字节相同」。配置对不对和构建认不认，是两件事。

### 分阶段，按风险排

| 阶段 | 内容 | 省 | 风险 | 怎么验 |
|---|---|---|---|---|
| 1 | 非中英文字体 + 裁 `fonts.xml` | 约 17 MB | 低（范围内已决定只做中英文） | 中文、英文、符号正常；日志里没有字体族错误 |
| 2 | 彩色 emoji | **约 6.9 MB** | 无：emoji 照样显示，只是单色 | 换成单色字体，不删。见下 |
| 3 | 相机 + DRM + CAS + media.metrics | 3.3 MB 盘 + 约 12 MB 内存 | 低 | 服务不在了；微信读书、浏览器照常 |
| 4 | RenderScript / LLVM | 13.77 MB | 中 | 要先确认没有应用在用 RenderScript |
| 5 | ICU 数据裁到中英文 | 最多 23.32 MB | **高**：时区数据在同一个文件里 | 日期、时钟、中文排序、输入法；错了就是钟不对 |
| 6 | 电话 / RIL、视频编解码 | 8.6 MB | 中 | 要逐个应用看会不会抛异常 |

### 第一、二阶段做了，三到六不做（2026-10-21）

一、二阶段的风险由机械守卫挡住：导出会拒绝「`fonts.xml` 点名了不存在的文件」，`tools/check-image-references.py` 查镜像里动态加载的文件和库依赖（那一版是 522 个文件、4544 条依赖），`tools/tests/test_font_config.py` 逐项核对配置与构建产物。

**一、二阶段的实测结果**：`/system/fonts` 173 个文件 43.00 MB → **37 个 33.0 MB**；`fonts.xml` 116 个 family → **15 个**；`usr/hyphen-data` 35 种语言 70 个文件 → **英文两种 4 个**。实际省下的是：字体 8.43 MB，emoji 换字体净省 5.30 MB（选了比估算时大的可变版，见下）。

**三到六不做。** 决定它的不是风险，是收益落在哪里：

- **镜像大小不在每次开机的等待路径上。** 系统镜像只在换过之后的第一次开机全读一遍（第一节，`SystemStamp.h`）：记录里的大小、mtime、簇分配、预期哈希四项全同就跳过重算，那 20 秒是**每个版本一次**；跳过全读的开机，在 `boot_completed` 之后 90 秒以最低的 CPU 和 I/O 优先级在后台复核一遍（`pw3-system-verify`）。所以砍镜像买到的是"每版一次的秒数"和下载体积，不是开机变快。
- **一、二阶段买到的不是体积，是 zygote 的活。** `Typeface.init()` 在静态初始化块里，`android.graphics.Typeface` 在 `preloaded-classes` 第 814 行：zygote 每次开机把 fonts.xml 里每个 family 走一遍——mmap、`addFontFromBuffer`、`FontFamily.freeze()`（读 cmap、建整张覆盖位图）。少 101 个 family 就是每次开机少 101 次，这在 1 GHz 单核上是实的。
- **三到六买不到这个。** `ZygoteInit.preloadSharedLibraries()` 只加载 `android`、`compiler_rt`、`jnigraphics`；`libRS`/`libLLVM` 要应用自己调 RenderScript 才加载，ICU 数据是 mmap、只有真读到的页才有代价。所以它们只省下载体积，却要换来「应用调 RenderScript 就崩」和「时区/排序行为变化」。按奥卡姆剃刀，不做。

### 第二阶段：彩色 emoji 换成单色字体（2026-10-21）

只去掉 `NotoColorEmoji.ttf`，书里和网页里的 emoji 会变成空方框。但**单色 emoji 字体有现成的**：上游的 Noto Emoji，SIL OFL 1.1，和镜像里已有的 Noto 系列同一个项目、同一类授权。AOSP 8.1 的 `external/noto-fonts` 里只有彩色版（`emoji/NotoColorEmoji.ttf` 7,279,008 字节，这一个进了 `/system/fonts`；`emoji-compat/NotoColorEmojiCompat.ttf` 另外 7.4 MB 是支持库的资源，**没有**进 /system，所以这一项是 7.28 MB 而不是 14）。

所以这一步是换掉，不是删掉：emoji 照样显示。而且单色本来就是 16 级灰面板上正确的呈现——彩色位图（CBDT）在这块屏上要抖成灰阶，分辨细节还不如单色矢量轮廓。

字体按大小和 SHA-256 固定在 `device/amazon/pw3/apps/prebuilts.json` 里（和 WebView、EinkBro 一样），由 `tools/fetch-prebuilts.py` 取并校验，不进仓库；`THIRD_PARTY.md` 里有一条 SIL OFL 1.1。

#### 选的是可变版，不是静态版

上游 `googlefonts/noto-emoji` 从 v2.038 起不再带静态单色版（最后一个是 v2.034 的 `NotoEmoji-Regular.ttf`，418,804 字节）；现在维护它的是 Google Fonts 的 `ofl/notoemoji/NotoEmoji[wght].ttf`，1,982,596 字节，权重轴 300–700。

两个都下来，按这台机器的真实字号（`ro.sf.lcd_density=300`，14 sp = 26 px、18 sp = 34 px、22 sp = 41 px）渲染并量化到 16 级灰，和彩色版并排比过：

- **彩色版在这块屏上确实是灰糊的**：⭐、☀️、✔️ 是淡灰色块，📚 是深灰污迹，14 sp 下几乎分不出彼此。两个单色版都是纯黑白，对比度完整。
- **静态版 vs 可变版是真有取舍**：静态版把符号画成实心（❤️🔥🌲✔️ 一眼可辨），但**脸画成实心黑团**，😀😂🙏 在 14 sp 下只剩一坨黑；可变版是描边，脸的表情留得住，实心符号则变成线描、更碎。
- 阅读场景里出现最多的是脸和手势（书评、笔记、网页正文），信息全丢的代价比符号变线描大，所以**选可变版**。多付 1.56 MB，相对彩色版仍净省 5.30 MB。
- 可变版的权重轴**钉在 500**：400 在 26 px 下笔画偏细，700 开始把树和太阳填实。`fonts.xml` 里用 `<axis tag="wght" stylevalue="500.0" />`，和 AOSP 自己的 `NotoSansKhmer-VF.ttf` 同一种写法——**可变字体在这份 fonts.xml 里本来就在用**，不是新机制。

#### 单色字体缺 cmap format 14 子表，补上了

单色字体没有 cmap format 14 子表，而 `FontFamily::hasGlyph(codepoint, variationSelector)` 在有变体选择符时**只读** `mCmapFmt14Coverage`。所以 Unicode 定义的 **351 条**「U+FE0F 写法」的 emoji（`❤️` 这种）全部会被报成画不出来，尽管绘制路径画得出来。先问再画的应用（`EmojiCompat` 走 `PaintCompat.hasGlyph`）会改用自己的字体。AOSP 的彩色字体带着全部 351 条。

补法：`device/amazon/pw3/emoji/add-emoji-variation-sequences.py` 从树里 `external/unicode/emoji-variation-sequences.txt`（AOSP 自己那份字体依据的同一个文件）生成子表，装进镜像的是「取来的字节 + 4,088 字节的表」。351 条的基字符这个字体**全都覆盖**。表写成 default UVS 记录（"支持，用普通 cmap 给的字形"），Minikin 的 `CmapCoverage.cpp` 把 default 和 non-default 合并成一张覆盖表，所以照样读得到。守卫是 `tools/tests/test_emoji_vs.py`：用一个与生成器不共用代码的解析器读回来，核对其余每张表逐字节不变、记录的序列恰好是 Unicode 那一组、子表注册在 platform 0 / encoding 5；改写前后 FreeType 渲染逐像素相同。

**写这个表的程序第一版把 `head` 表的目录校验和算错了**（先按原始字节算各表校验和，之后才清零 `checkSumAdjustment`，而目录项不会再被修正；OpenType 规定的顺序正相反）。开发期间有一版镜像带着这个错值——从导出镜像里取出字体查过，目录里是 `0x7bacb7ad`，规范值是 `0x2832657a`。整文件校验和一直是对的，所以只查那一个查不出来。没有证据说 Android 8.1 会因此拒绝这个字体，但它不符合规范，而且是要发布的字节，所以改正后重新构建；前后两版字体只差 8 个字节（`head` 的目录项校验和与 `checkSumAdjustment`）。现在测试逐表校验和都查，`head` 不跳过。

**删减丢了哪些码点，是量出来的**：把 AOSP 原配置的 173 个字体条目和本项目 37 个条目的 cmap 全解出来取差集，与中英文排版相关的 27 个范围（含 CJK 统一汉字 20945、扩展B 2051、半宽全宽 225、通用标点 100、箭头 112、制表符 128、数学 256、杂项符号 256、装饰符号 191、带圈数字 160）**每一个都丢 0 个**；丢的 12328 个里 9384 个是不排版的那些文字的字母本身，符号与数字形式类 539 个（按 Unicode 类别数和按 cmap 差集算，两条路径结果一致），其中货币符号 11 个。

#### 砍掉的文字自带的货币符号，按范围记下

`֏ ؋ ৲ ৳ ৻ ૱ ௹ ฿ ៛ ﷼ ꠸` 这十一个不再有字体覆盖，其中实际在用的是 ฿、৳、﷼。要覆盖这三个得把泰文、孟加拉文、阿拉伯文加回去（约 238 KB、zygote 每次开机多三次字体族加载），不划算。

但范围是**被检查的**，不是口头的：`tools/tests/test_font_config.py` 的 `COVERAGE` 列出 18 组「这套字体必须能画的码点」，直接读装进镜像的字体文件的 cmap 核对，0.13 秒。以后任何精简碰到这些会当场失败，而不是到设备上显示方框。

### 镜像里最大的一块是不可压缩的（2026-10-21 量过）

478.5 MB 都在哪：

| 位置 | 体积 |
|---|---|
| `app/SystemWebView`（APK 本体 86.63 MB） | 95.2 MB |
| `lib`（含 `libLLVM.so` 11.41 MB） | 94.1 MB |
| `/system/framework` 下的 ART 启动镜像（arm；**不能动**，动了 `/data` 里的机器码全失效） | 65.2 MB |
| `fonts`（精简后降到 33.0 MB） | 43.0 MB |
| `app/EinkBro`（odex 21.80 MB） | 30.5 MB |
| `usr/icu/icudt58l.dat` | 23.3 MB |

第一名拆开看：`SystemWebView.apk` 86.63 MB 里 **73.64 MB 就是 `lib/armeabi-v7a/libwebviewchromium.so` 一个文件**，而且它在 APK 里是 `stored`（WebView 加载器要直接 mmap，必须页对齐不压缩），所以在镜像里也是满额。节区：`.text` 58.7 MB、`.rodata` 8.4 MB，**没有 `.symtab`、没有任何 debug 节——已经剥离过**。只有一个 ABI。能省的只有 `assets/stored-locales/` 里 79 个用不到的语言包，约 1.3 MB——为这点体积去重签一个第三方 APK 不划算。

**结论：镜像体积的下限由 Chromium 决定，不由我们决定。** 除非自己编 Chromium，否则 95 MB 是地板。

## 八、登录之后的微信读书：一次完整的实测（2026-10-27）

前面几节量的都是装好但没登录的状态。这一节是扫码登录、书架上有书之后，在同一台设备上量的。线插着，屏幕用 `svc power stayon true` 按住不灭，每组计时前确认屏幕醒着（第五节第一条）。

### 使用者看到的四个动作

| 动作 | 到完全安静 | 应用自己的 CPU | 下载 |
|---|---|---|---|
| 冷启动（恢复到在读的那本书） | 约 40 s | 28 s | 约 16 MB |
| 从书架打开一本从没下过的书 | 51 s | 31 s | 0.6 MB |
| 再打开同一本书 | 约 20 s（30 s 全静） | 11 s | 0.13 MB |
| 翻一页 | 1 s 以内 | 0.44–0.81 s | — |

「安静」的判据是进程的 `utime+stime` 连续三次采样、每 5 秒涨不到 200 毫秒。冷启动那一行和第六节的「约 37 秒到书架」是同一个量级，所以登录带数据之后没有退化。

那约 16 MB 每次冷启动都要重下一遍，而两次冷启动之间 `/data` 只涨了 540 KB，说明它没有落盘。这是应用自己的同步行为，系统这边改不了，但它占掉冷启动 40 秒里的 16 秒。

### 不是什么

**不是网络。**Wi‑Fi 信号强，到 `weread.qq.com` 四包 0% 丢包、延迟 6–95 ms。冷启动那 16 MB 是 16 秒下完的，1.08 MB/s。而打开一本新书只下了 634 KB 却花了 31 秒 CPU——那一步几乎不碰网络。

**不是调速器。**这颗 CPU 只有 996 MHz 和 396 MHz 两档，开机以来 87% 的时间停在 396 MHz，`ondemand` 的 `up_threshold` 又是按当前频率算负载的 80，看起来很可疑。把 `time_in_state` 和 `/proc/stat` 放在同一个 54 秒窗口里对账：996 MHz 36.4 秒，全机忙 35.1 秒；396 MHz 17.6 秒，空闲（含 iowait）18.9 秒。两边几乎正好对上，**有活就满频、没活才降**，落在 396 MHz 上的「有活干」时间下界是 0。这一条已经排除。

**机器码没有失效。**`dumpsys package dexopt` 报 `kOatUpToDate`，机器码没有因为启动镜像变动而失效。**这一条值得每次发行后在设备上核一次**：开发期间遇到过启动镜像变了、`/data` 里的机器码全部失效，打开一本书要 53.7 秒，表面上和「硬件就是这么慢」一模一样。编译级别本身的影响见第十二节（这次也把整包编到 `speed`——20 分钟 CPU，`/data` 多 98 MB——量过一次，数没有明显变化；那次没有交替对照，以第十二节为准）。

**不是系统里还有冗余。**除微信读书外全部进程的 PSS 加起来约 120 MB：surfaceflinger 31.5、system_server 27.9、SystemUI 14.2、Launcher3 7.3、android.process.media 5.6、拼音输入法 2.6，其余每个都在 1 MB 以下。没有可砍的大块。微信读书自己是 128.8 MB，加上它的 `:seg` 进程 22.0 MB，共 151 MB，一台 511 MB 的机器。

**不是 SwiftShader 在画。**微信读书和 Launcher3 都没有 RenderThread（SystemUI 有一条）：本系统的产品策略（`ro.pw3.software_canvas=true`，第三节）让应用窗口走软件 Canvas，不经过 SwiftShader。上面那 31 秒里没有一帧是 SwiftShader 画的。

### 登录后第一次同步：慢 2.75 倍，差的全是内存

登录成功之后第一次同步时量到的是：`MemFree` 一度只剩 5,940 KB，zram 换出 115 MB，一次加载里 `pgmajfault` 涨了 1,423，整次冷启动烧掉 72 秒 CPU、墙钟 110 秒。而同一个冷启动在同步做完、内存回到 221 MB 空闲之后只要 40 秒。**同一台机器、同一个应用、同一个账号，差 2.75 倍，差的全是内存。**这是一次性的，但它恰好落在使用者第一次用这台设备的那十几分钟里。

### 一个确实归我们、但不建议动的数

打开一本新书的那 18 秒里，主进程做了 5 次并发复制 GC，各 902 / 956 / 1938 / 543 / 493 毫秒，合计 4.83 秒；`:seg` 进程另有一次 853 毫秒。每次收集时堆都是「34–36% free, 28–30MB/44–46MB」——存活约 30 MB，余量 16 MB。这 16 MB 是 `dalvik.vm.heapmaxfree=8m` 乘前台倍率 2 来的，而 `pw3.mk` 堆参数旁记的那条经验（收集约 0.02 秒/MB 存活；余量约等于存活堆时 GC 占一成）要求的余量在 30 MB 上下。

把 `heapmaxfree` 提到 `16m`，余量变 32 MB，收集次数约减半，省约 2.4 秒——**51 秒里的 5%**，代价是每个前台应用多占最多 14 MB，在一台 511 MB、刚刚因为内存不够慢过 2.75 倍的机器上。按奥卡姆剃刀不值得。同一个问题按整次冷启动重算见第十节。

### 剩下的 26 秒还是没拆开

打开一本新书的 31 秒 CPU，扣掉 4.8 秒 GC，还剩约 26 秒不知道花在哪。按线程分，冷启动那次是主线程 25.0 秒、`WRCommonPool` 四条共 14.8 秒、`RxComputationScheduler` 3.6 秒、`WRNetworkPool` 四条共 6.2 秒、`HeapTaskDaemon` 1.7 秒、JIT 线程池只有 0.3 秒（JIT 线程闲着不能说明没有解释执行，见第十二节）。再往下拆要用 simpleperf（第九节）。

## 九、还没量的

- 常态开机（镜像没变的那次）是不是约 31 秒：第一节是按 52 − 20.9 算的，没有单独量过。
- `services.jar` 现在是 `speed-profile`（Android Go 的默认，为省空间），它是每次交互都要走的代码；改成 `speed` 值不值，没有上机比过。
- 翻页时整屏合成到底多少毫秒（第三节的 10.6 ms 是 93 次呈现的平均，而那些呈现大多只更新状态栏那一小块）。
- 打开一本书时应用自己的 CPU 花在哪：机器码在用、读盘只有约 90 MB（约 3 秒），第八节按 GC 和线程拆到了头，剩下的是类加载、静态初始化、应用自己的初始化还是换页，分不开。要用 simpleperf 看，而设备上没有，`user` 构建也不允许采样非 debuggable 的应用。

## 十、还能不能让微信读书更快：按整核对账（2026-10-28）

第八节按动作量了耗时，这一节回答下一个问题——**这些时间有多少是我们能动的**。

**量法。** 冷启动直接恢复到上次打开的测试书（约 800 页），所以一次冷启动就是一次完整的「开书」，不必点击，坐标也不会漂。「安静」的判据是进程的 `utime+stime` 连续两个 2 秒区间涨不到 0.15 秒。每一组开始前读一次 `dumpsys power | grep mWakefulness=`（第五节第一条）。关键在于**把 `/proc/stat` 和 `/proc/<pid>/stat` 放进同一个窗口对账**，这样「应用不在 CPU 上」就不再是一个余数。

### 进程的 CPU 要按进程读，不能按线程加

按 `/proc/<pid>/task/*/stat` 把线程累加起来当作进程的 CPU，**会漏掉运行期间已经退出的线程**：同一次开书，按线程加是 53.3 秒，按 `/proc/<pid>/stat` 是 74.2 秒，少算三成，看起来就像有三到四成时间不在 CPU 上。按进程读，**没有缺口**。

### 整核的去向

95 秒的窗口（冷启动到完全安静）：

| | 时间 | 占墙钟 |
|---|---|---|
| 微信读书 | 74.2 s | **78%** |
| 其他所有进程 | 14.0 s | 15% |
| `:seg` 分词进程 | 2.1 s | 2% |
| 核空转 | 4.2 s | 4% |
| 其中等盘（iowait） | 0.0 s | **0%** |

把「其他」拆开，另一次 79 秒的窗口：整核忙 74.6 秒（94%），微信读书 54.4 秒（69%），`surfaceflinger` 2.7 秒（3%），`:seg` 1.8 秒（2%），`system_server` 1.2 秒（2%），SystemUI 0.1 秒，**未归属 14.4 秒（18%）**。未归属的那部分是内核线程、Wi-Fi 软中断和 eMMC 驱动，按进程读不出来，没有再拆。

两次里微信读书自己占 69%–78%，**等待就是它在单核上算**。

### 排除掉的

- **不是运行时编译。** 单次冷启动里 JIT 线程池只用了 0.0–0.6 秒。此前在设备上读到的「JIT 线程池 21.3 秒」是**整整 18 分钟一段会话**的累计（登录、首次同步、下载、连开数本书），不是一次开书的代价。注意这只排除了 JIT 编译本身，**不排除解释执行**：解释执行的开销记在执行代码的线程上，不经过 JIT 线程（第十二节）。
- **不是合成。** `surfaceflinger` 2.7 秒 / 79 秒 = 3%。这台机器没有 GPU、整屏窗口一帧 6.2 MB 要 CPU 搬，所以这条值得查，查完可以关掉。
- **不是分词服务。** `:seg` 1.8–2.1 秒 = 2%。它是独立进程、每次调用都是 binder 往返，所以也值得查，同样可以关掉。
- **不是没开 NEON。** `BoardConfig.mk` 是 `armv7-a-neon` / `cortex-a9`，设备 `/proc/cpuinfo` 的 Features 里有 `neon`。
- **不是等盘。** 整个窗口 iowait 为 0。
- **不是网络。** 期间收了 18.5 MB，但核空转只有 4%–6%，**下载全程和计算重叠**，没有一段是停下来等传输。

### 运行时的另一个杠杆：垃圾回收的余量

每次开书 8–9 次并发复制回收，三次合计 **11.4 / 12.8 / 13.8 秒**，占应用自己 CPU 的 17%–25%。回收时堆一直是「存活 19–30 MB，占用 32–46 MB」，余量 16 MB —— `dalvik.vm.heapmaxfree=8m` 乘前台倍率（`foreground-heap-growth-multiplier=1.0`，ART 的并发收集器再加 1）。

**为什么分配这么多。** 这本测试书约 800 页、三十多万字，整次分配接近一百兆，折合**每排一个字约 250 字节**（逐字的 `CharElement` / `Paragraph$Word`、`int[]`、装箱）。这和实测对得上：每 9.6 秒一次回收、每次释放 8–16 MB、每次清掉 23 万–37 万个对象。回收的代价跟**对象个数**走而不是字节数，所以总开销由**次数**定，而次数 = 分配总量 ÷ 余量 —— **余量正是我们设的那个值**。

余量加倍则次数减半，约省 6 秒 / 95 秒 = **6%–7%**。这比第八节那笔账（省 2.4 秒 / 51 秒）大，因为那次量的是「打开一本新书」的 18 秒片段，这次是整个冷启动。而且**动倍率比动 `heapmaxfree` 便宜**：`foreground-heap-growth-multiplier` 只作用于前台那一个进程，`heapmaxfree` 每个进程都要付。AOSP 自己的默认是 2.0，`pw3.mk` 按 Android Go 的做法设成了 1.0。

**代价是前台应用多占内存，而这台机器并不宽裕**：测量时 `MemFree` 43 MB、zram 已用 125 MB，期间拼音输入法和 `:seg` **都被杀过**（`has died: prcp IMPB` 和 `cch CEM`，`logcat -b crash` 是空的，所以是被杀不是崩溃）。

**2026-10-29 上机配对量过，两臂分不开。** A B B A 四轮，A＝倍率 1.0（余量 16 MB），B＝2.0（余量 24 MB，和 AOSP 给 1 GB 手机的一样）。每轮：改属性 → 重启框架（`dalvik.vm.*` 是 zygote 启动时读的，只 `setprop` 不生效）→ 丢页缓存 → 强停微信读书 → 点图标冷开同一本书 → 固定 115 秒窗口后读进程 CPU 和回收记录。A 臂两轮几乎一样（都是 7 次回收，回收 6.9 / 6.1 秒，RSS 相差 57 KB）；B 臂两轮回收 2.3 / 11.2 秒，第二轮进程 CPU 30.4 秒、是其余三轮的两倍——那一轮应用自己干的活就不一样（多半是联网同步），不是倍率造成的。两对配对差符号相反（−4.6 秒和 +5.1 秒），这组数据不支持任何结论；四轮全程没有低内存杀进程。所以倍率保持 1.0。再测要先把工作量控住：断网、固定书和页码、每臂至少三轮。

### 这台机器上剩下的，不在系统侧

编到 `speed` 之后（第十二节），开书时应用自己的约 30 秒 CPU 是它在单核上做的解析、排版和同步。页脚显示的是「第几页 / 全书共几页」，说明它在算**全书页码**；微信读书里「阅读进度」如果能切成章节或百分比，整本排版这件事本身可能就跳过了。那是应用内的设置，**没有试过**。

> 不经过面板驱动，所以它既不是"面板上最后那一帧"，也不能和面板计数器做差。
> 要知道面板上是什么，只有三条路：让使用者看、`userdebug` 上开 `mxc_epdc_debug`、
> 或者只用面板计数器说"更新了几次、每次多大"。下面的数字作为帧缓冲内容的记录仍然有效。

测第十节时，在冷启动过程中按固定时刻截了五帧。PNG 的体积先把问题暴露出来（整屏纯黑压得极小，正文页压不动）：

| 时刻 | PNG | 画面 |
|---|---|---|
| t=24 s | 18 KB | 整屏纯黑 |
| t=32 s | 14 KB | 整屏纯黑 |
| t=48 s | 244 KB | 正文 |
| t=57 s | 244 KB | 正文 |
| t=79 s | 241 KB | 正文 |

另一次按暗像素比例采样，得到同样的形状：t=17 s 是 6.8%、t=32 s 是 87.5%、t=50 s 起稳定在 7.1%。**两次都是二十秒以上的纯黑，中间没有任何过渡。**

### 黑的那一刻，谁都没有在画

在黑的中段（启动后 26 秒）读窗口和层：

```
Window{… com.tencent.weread.eink/…ReaderFragmentActivity}
    mHasSurface=true  isReadyForDisplay()=true
    mDrawState=DRAW_PENDING          ← 一帧都没画
Layer (…ReaderFragmentActivity#0)
    activeBuffer=[0x0: 0, 0]  queued-frames=0   ← 这一层没有任何缓冲
Window{… com.android.launcher3/…Launcher}
    mDrawState=HAS_DRAWN  mLastHidden=true      ← 上一屏已经被隐藏
```

壁纸层也没有缓冲。**前台窗口没有内容，上一屏被隐藏，合成出来的就是黑** —— 那片黑不是谁画的，是没有任何人画。

### 来源是补丁 0008，而它的前提不成立

`0008-pw3-no-starting-window-opaque-surfaces.patch` 用 `ro.pw3.disable_starting_window` 让 `ActivityRecord.showStartingWindow()` 直接返回。设备上这个属性是 `true`。补丁写的理由是：

> 预览窗口要自己的缓冲（每个 6 MB）、一次整屏绘制、一次 134 毫秒以上的墨水屏更新，之后立刻被应用的第一帧取代。**上一屏会一直留着，直到那一帧。**

**最后那句话在 SurfaceFlinger 的层面不成立。** 上面的窗口状态直接否掉了它：`mLastHidden=true`，上一屏已经隐藏。补丁末尾自己也记着「Not run on the device yet when this patch was written」。

在手机上这无关紧要——应用两三百毫秒就画出第一帧。在这台机器上应用要二十到四十五秒，于是帧缓冲里有二十秒以上的纯黑。只是这些黑帧没有推上面板（见下），所以省下的 134 毫秒面板更新仍然是实的。

### 两条改法

现在那二十秒面板什么都不做；把启动窗口放回来反而会让面板多一次整屏更新，所以**现状可能已经是对的**。要改的话有两条，都没有在真机上验证过：

1. **把启动窗口放回来**（属性置 `false`，或撤掉补丁的第一半）。代价是每次启动多一次整屏面板更新（134 毫秒以上）。**颜色未定**：启动窗口画的是该 Activity 主题的 `windowBackground`，微信读书的主题是白是黑没有查过——如果它本来就是黑的，这条改法解决不了问题。
2. **保持不画启动窗口，但让上一屏真的留到新应用画出第一帧**——这才是补丁原本想要的行为，代价是改窗口过渡的逻辑，比第一条大。

### 面板上实际看到的：白屏，然后一次黑闪

使用者看着的两次冷启动（`speed` 状态），帧序列都是 10.2% → 91.7% → 100% → 6.1%，和上面一样。而面板上是先白屏、正文出来时黑闪一下。所以面板停在第一张（10.2% 暗，基本全白的加载页），中间那些黑帧**一次也没有推上去**。

**帧缓冲不是面板。** `screencap` 读的是 SurfaceFlinger 的合成结果，不是这块屏上现在显示的东西；墨水屏不被推新帧就保持上一画面。本仓库为波形记过同一类教训（请求的波形不等于执行的波形），这是同一类错误的另一个方向。**凡是关于"屏幕上是什么"的结论，都要由看着屏幕的人确认，或者由内核日志确认。**

那一下黑闪是 `device/amazon/pw3/epdc/Panel.h` 的 `replaced()`。一个窗口出现或消失时，该区域被记满欠账，由画出新内容的那次更新一次 GC16 还清。它的来历是 Wi‑Fi 密码对话框消失后用 GL16 重画、残影留在列表下面（2026-10-23）。所以微信读书的阅读窗口第一次画出来算「新窗口出现」，整屏一次 GC16，**这是设计内的，而且设计目标就是"只闪这一次"**。要不要改是另一个问题，但它不是缺陷，也不是启动窗口那条造成的。

### 还有一件没查清的

2026-10-28 遇到过一次：书下载完以后，页面还停在「加载中」。当时抓到的帧缓冲里已经是**排好的正文页**，应用的 CPU 从那以后一个滴答都没再动，而设备近十分钟后才自动休眠，这段时间屏幕一直亮着。那一刻 SurfaceFlinger 记的是 `activeBuffer=[1072x1448:1072, 2]  queued-frames=0`，缓冲已经被消费。**排好的那一帧为什么没有出现在面板上，没有查清，也没有再现。** 要查清得在它出现时当场抓 `dumpsys SurfaceFlinger` 和 `/sys/class/graphics/fb0`（后者 shell 读不到，要 userdebug 镜像或提权）。

## 十二、全量机器码把开一本书的时间减掉一半（2026-10-28）

第六节的六轮配对量的是登录前、书架空的冷启动。这一节按一次完整使用来量编译级别：加载书架、打开一本书。起因是使用者反映设备比最早用的时候慢。

**量法。** 同一台设备、同一个已登录的账号和书架，从首页**点图标**（不是 `am start`）。顺序是 A A B B A A：先在 `speed-profile` 量两轮，编到 `speed` 量两轮，再编回 `speed-profile` 量两轮。每次编译之后**静置 3 分钟**，因为第六节记过：紧跟在满核 dex2oat 之后的那一轮不可比。

| 轮 | filter | odex | 点图标到安静 | 进程 CPU | GC |
|---|---|---|---|---|---|
| 基线A | `speed-profile` | 7.1 MB | 99.8 s | 77.6 s | 9 次 10.3 s |
| 基线B | `speed-profile` | 7.1 MB | 88.9 s | 69.7 s | 8 次 11.6 s |
| **B1** | **`speed`** | **100.3 MB** | **55.4 s** | **30.8 s** | 9 次 11.5 s |
| **B2** | **`speed`** | 100.3 MB | **47.3 s** | **29.5 s** | 10 次 8.0 s |
| A3 | `speed-profile` | 1.0 MB | 104.8 s | 74.3 s | 8 次 12.6 s |
| A4 | `speed-profile` | 1.0 MB | 89.0 s | 70.5 s | 9 次 15.5 s |

**墙钟 95.6 → 51.4 秒（少 46%），进程 CPU 73.0 → 30.2 秒（少 59%）。** 四轮 `speed-profile` 落在 88.9–104.8，两轮 `speed` 落在 47.3–55.4，**两组不重叠**。之后把设备编回 `speed` 并另外量了两轮，是 56 秒和 50 秒，和 B 组一致。

**三件事让这个结果站得住：**

1. **收尾的 A3/A4 回到了 89–105 秒**，说明这一小时里机器没有漂，差值不是时间顺序造成的。
2. **偏差方向对结论不利。** 两轮 `speed` 紧跟在 1279 秒满核 dex2oat 之后（只静置了 3 分钟），按第六节那条这本该让它吃亏；它还是快了一倍。
3. **GC 几乎没动**（A 组 10.3–15.5 秒，B 组 8.0–11.5 秒）。省掉的 43 秒全在应用自己的 CPU 里，**那就是解释执行的开销**。

### 第六节那六轮为什么没看出来

它量的是**登录前、书架空的冷启动**（约 37 秒）。那条路径上要跑的代码少得多，而且多半已经在画像里。「加载书架、打开一本书」要跑的是 EPub 解析、CSS 解析、逐字排版——这些方法画像里没有，于是全程解释执行。**同一个应用，两种工作量，结论相反**；第六节的数没有错，它回答的是另一个问题。

**JIT 线程闲着不说明没有解释执行。** JIT 线程只负责*编译*；没有机器码的方法在**解释器**里跑，那份开销记在执行它的线程上，根本不经过 JIT 线程。第十节量到 JIT 线程池只用 0.0–0.6 秒，恰恰可能意味着代码正在被解释执行。

### 代价

| | `speed` | `speed-profile` |
|---|---|---|
| 编译一次 | 1250–1279 秒 | 144 秒 |
| odex | 100.3 MB | 1.0–7.1 MB |
| 常驻内存（第六节） | 210.6 MB | 181.1 MB |

`/data` 用掉 786 MB、还剩 978 MB，放得下。多出的常驻内存在一台会杀输入法的机器上不是小数，所以这一条要和第十节的 GC 余量一起权衡；这个数里大部分是什么，见下面验证的第五条。在 `speed` 下总 CPU 只有 30 秒而 GC 还是 8–11.5 秒，**GC 从占应用 CPU 的六分之一变成三分之一**，那条杠杆反而变重了。

### 设计：安装用 `quicken`，空闲时编到 `speed`

安装仍用 `quicken`（约两分钟，第六节末）；设备空闲时由后台编译任务编到 `speed`（`pw3.mk` 里 `pm.dexopt.bg-dexopt=speed`），编一次长期有效。Kindle 绝大部分时间是空闲的。照搬 AOSP 有两个障碍，各由一个补丁解决：

- **AOSP 的后台编译任务要求设备空闲且插着充电器**，Kindle 上很少插着充电器。`patches/aosp-frameworks-base/0066` 把「插着充电器」换成「电量不低」，「设备空闲」保留。
- **dex2oat 是就地覆盖的。** installd 先删掉旧产物再新建（2026-10-28 编译进行中的读数见下）。旧的机器码在编译一开始就没了，整个编译窗口里这个应用处于 `invalid`——此时打开它，**一行机器码都没有，全部解释执行**，比不编还慢；编译中断时 installd 的清理回调还会把半成品删掉，应用新旧机器码都没有。而使用者一碰设备，后台任务就会被取消，二十分钟的编译很容易被打断。`patches/aosp-frameworks-native/0009` 让每个产物先建在 `<路径>.staging`，dex2oat 成功后再原子改名换上（oat 放最后），没编完就什么都不动。

```
base.odex   0.6 MB   ← 从 0 开始长，终点 100.3 MB
dumpsys package dexopt →  arm: invalid[]
```

放弃的是参考画像（只有按画像编的级别才会写出它）。这里用不上它：`speed` 编全部方法，按画像编附带的应用镜像量过只值约 0.4 秒（第六节）。镜像自带的应用不受影响：它们都已按 `speed` 预编译（`PRODUCT_DEX_PREOPT_DEFAULT_COMPILER_FILTER`），后台任务不会把它们重编进 `/data`。

### 真机上的验证（2026-10-28）

**一、不变量在设备上成立。** 把微信读书从 `speed` 编回 `quicken`，整段过程每 10 秒看一次：

| 时刻 | 正式的 `base.odex` | `.staging` | `dumpsys package dexopt` |
|---|---|---|---|
| 编译前 | 105,193,896 | — | `kOatUpToDate` |
| 10 s | **105,193,896** | 0 | **`kOatUpToDate`** |
| 20–60 s | **105,193,896** | 596,372 | **`kOatUpToDate`** |
| 70 s | 1,057,192 | 已清掉 | `kOatUpToDate` |

改之前同一件事是：`base.odex` 从 0 开始长，整整二十分钟 `arm: invalid[]`。

**二、任务的条件按新的注册了**：`Requires: charging=false batteryNotLow=true deviceIdle=true`。

**三、设备自己编了。** 把它留在 `quicken` 状态、屏幕灭着放着，每 10 分钟只读查询一次（`dumpsys` 不算用户活动，不打断空闲计时）：

```
第 0 分钟    IDLE 不满足        filter=quicken
第 10 分钟   IDLE 满足          filter=quicken     ← 任务启动
第 20 分钟                      filter=quicken     ← 编译中
第 30 分钟                      filter=speed       ← 编完
```

屏幕灭满 71 分钟（`IdleController` 的 `INACTIVITY_IDLE_THRESHOLD`，外加最多 5 分钟窗口浮动）之后任务启动，约二十分钟编完 100.3 MB 的 odex，`kOatUpToDate`，没有临时文件残留。**全程没有人碰设备。**

**四、开书时间。** 两轮：65.9 s / CPU 38.5 s，54.6 s / CPU 31.0 s。对照上表的 `speed-profile` 四轮 88.9–104.8 s / CPU 69.7–77.6 s。第一轮偏高是页缓存冷——设备刚空闲完，100 MB 机器码要从 eMMC 读上来；第二轮与手动编出的那组（47–56 s / CPU 29.5–30.8 s）重合。**CPU 从 70 秒出头降到 31 秒。**

**五、常驻内存：第六节那个差说的不是一回事**（2026-10-28 晚，微信读书在 `speed`、刚冷启动过一次）：

```
.oat  mmap     3,245 KB   ← 100.3 MB 的机器码，常驻只有 3.2 MB
.dex  mmap    63,201 KB
.art  mmap     1,944 KB
Dalvik Heap   20,882 KB
TOTAL        142,877 KB（139.5 MB）
:seg          21,327 KB
全机：MemFree 50 MB，Cached 269 MB，zram 用掉 73 MB
```

**机器码是文件映射，不是读进内存的。** 100 MB 的 odex 里常驻的只有真正执行到的 3.2 MB，而且那是**文件页**——内存紧张时内核可以直接丢掉，要用再从盘上读回来。会把别的进程挤到被杀的是匿名内存（堆），而 `speed` 几乎不增加匿名内存。所以第六节记的常驻内存差（`speed` 比 `quicken` 多 23 MB、比 `speed-profile` 多 30 MB）量到的是别的东西（读数的条件没有记下来），不能直接当成「这台机器会因此更容易杀进程」的依据。

连续几天普通使用下是否更容易杀进程，**尚未验证**。设备自己记着这方面的数据（`dumpsys procstats --hours 24` 和事件缓冲区里的 `am_kill`）。

**六、头两个半小时的基线（2026-10-28 起，每半小时一次只读采样，`speed`）**：

```
MemFree      37–51 MB     稳定
Cached      262–267 MB    稳定
zram 用掉     71–73 MB     没有增长
pswpout      49531 → 49531   整段时间一页都没有换出
pgmajfault   2.5 小时涨了 169
被杀的进程    0
```

这段时间设备以空闲为主，所以它**不是结论，是基线**：说明 `speed` 在静息状态下不制造内存压力，和「机器码是文件映射」那条推理一致。

**一条行为**：日志里有 `JobServiceContext: Client timed out while executing (no jobFinished received), sending onStop`。JobScheduler 给一次执行的额度是 10 分钟，而编一个微信读书要二十分钟，所以中途一定会收到停止信号。编译仍然能编完，因为 `abortIdleOptimizations()` 是在**两个包之间**检查的，不打断正在跑的那一个。代价是：要编的包不止一个时，一个空闲窗口只编得完第一个，其余留到下一次。这台机器上要编的只有使用者自己装的那几个，所以够用；但它是行为，不是巧合，写在这里免得以后当成缺陷查。

另外，dex2oat 的 nice 是 10，而且**不在后台 cpuset 里**（`cpuset:/`、`cpu:/`）。按 CFS 权重，前台应用约能拿到九成的核，编译掉到一成速度——所以它不会把设备卡死，但两边都慢。
