# 在本机安装大型应用（以微信读书为例）：调研与方案

手动安装（按腾讯的官方步骤）和自动安装（系统自带的下载器）两条路径的设计，以及装上前后应用的代码怎么编译。2026-10-16 起调研、实测；各项改动所在的补丁在对应小节注明。

## 要什么

- 微信读书不能随系统分发（腾讯的私有软件），开源发行版里由使用者自己装。
- 装法要普通使用者做得来。最好就是腾讯给"其他墨水屏设备"写的官方步骤，不另编一套。
- 装完要好用：打开应用、打开一本书，不能因为代码没有编成机器码而明显变慢。

## 腾讯的官方步骤

[微信读书墨水屏版安装指引](https://ink.qq.com/ink/guide)：
1. 在电脑上下载安装包；
2. 用数据线连上，设备处于"USB 文件传输模式"；macOS 要用 Google 的 Android File Transfer；
3. 把安装包拷进设备；
4. 在设备的文件管理器里打开，选"安装"。

本系统对应的能力：
- USB 文件传输：MTP（`docs/design/usb-mtp.md`）。没有锁屏密码时插线即可传文件，不用点通知。
- 文件管理器："文件"应用（DocumentsUI）。第一次从它安装应用时，8.1 会请使用者在设置里允许"文件"安装未知应用。这是 AOSP 原样的流程。

## 装的时候编译什么

顺序和普通安卓手机一样：先装上、能用，设备闲下来再编机器码。不同的是后台编到哪一级、什么条件下编。

| 时刻 | 编译级别 | 在哪设置 | 微信读书 2.1.2 实测 |
|---|---|---|---|
| 安装时 | `quicken`：不出机器码，只把 dex 快速化 | `pm.dexopt.install`，用 AOSP 的默认值，`pw3.mk` 不覆盖 | 编译 72–93 s（五次），产物 76 MB |
| 设备空闲时 | `speed`：所有方法都编成机器码 | `pm.dexopt.bg-dexopt=speed`（`pw3.mk`） | 编译约 20 分钟，产物 176 MB |

后台这一步由 AOSP 的空闲编译作业（`BackgroundDexOptService`）完成。这个作业原样搬到 Kindle 上几乎不起作用，本项目改了三处：
- 级别：AOSP 用 `speed-profile`，只编使用画像里记下的方法；这里改成 `speed`（`pw3.mk`，2026-10-28 起），理由见下一小节。
- 条件：AOSP 要求设备空闲并且在充电。Kindle 一次充电用几周，这个条件几乎不成立，作业就不跑，应用一直停在 `quicken`。frameworks/base 0066 把"在充电"换成"电量不低"，"设备空闲"保留。
- 中途打断：AOSP 的 installd 一开始编译就删掉旧产物、在原处写新的，整个编译期间应用没有机器码，被打断还会新旧都没有。frameworks/native 0009 让每个产物先写到 `<路径>.staging`，dex2oat 成功后再逐个原子改名换上（oat 最后换），所以任何时刻应用都有一整套旧的或新的代码。

使用者拿起设备时作业会被取消；还没停下的 dex2oat 以 nice 10 运行（installd 本来的设定），前台应用约能拿到九成 CPU。

真机实测（2026-10-28）：作业按新条件注册（`charging=false batteryNotLow=true deviceIdle=true`）。微信读书留在 `quicken`、屏幕熄灭放着，约 71 分钟后设备进入空闲、作业启动，约 20 分钟编完 100.3 MB 的 odex，没有残留临时文件，全程没有人碰设备。另一次编译时每 10 秒查一次，正式的 `base.odex` 在新文件换上之前一直是原来那份，`dumpsys package dexopt` 一直报 `kOatUpToDate`。后台在电池上编译一次的耗电和发热尚未在真机上量过。

### 为什么这样分

| 测量 | 比较 | 结果 |
|---|---|---|
| 登录前、空书架的冷启动（2026-10-20，六轮配对，每次启动前清页缓存） | `quicken` 对 `speed` | `quicken` 慢 3.9 s（95% 区间 0.3–7.5 s，p = 0.04） |
| 同样的冷启动，另一组六轮配对 | `speed-profile` 对 `speed` | `speed-profile` 慢 2.0 s（95% 区间 −2.1–6.1 s，p = 0.28） |
| 一次使用：从首页点图标、加载书架、打开一本书（2026-10-28） | `speed-profile` 四轮对 `speed` 两轮 | 95.6 s 对 51.4 s；进程 CPU 73.0 s 对 30.2 s；两组不重叠 |

- 安装时不编 `speed`：要 20 分钟，期间 CPU 占满、空闲内存只剩约 6 MB（见下一节），设备正好在使用者点了"安装"的时候没法用；换来的只是冷启动快几秒。曾以"没有机器码时微信读书要 129 秒才到书架、还弹'无响应'"为由在安装时全编；那是调大 Java 堆余量之前的测量，之后不复现（约 41 秒，没有弹窗）。
- 后台编 `speed` 而不是 `speed-profile`：两组冷启动看不出差别，是因为登录前、空书架的冷启动要跑的代码少，多半已在画像里。加载书架、打开一本书要跑 EPub 解析、CSS 解析和逐字排版，这些画像里没有，于是全程解释执行。GC 几乎没变（10.3–15.5 s 对 8.0–11.5 s），差出来的 43 s 就是解释执行的开销。
- 代价：微信读书在 `/data` 多占约 99 MB（实测时还剩 978 MB）；常驻内存的影响见 `performance.md` 第十二节。`speed` 不写参考画像，这里也用不到：只有按画像编译才生成应用镜像，而应用镜像只值约 0.4 s（见下一节）。

## 全量编译一次的开销（实测）

后台作业编到 `speed` 时做的就是这件事。2026-10-16 用 `cmd package compile -m speed -f` 实测：

| 项 | 实测 |
|---|---|
| 本机全量编译微信读书（13 个 dex，70.5 MB） | **1199 s（20 分钟）**，CPU 全程占满 |
| dex2oat 内存 | 常驻约 270 MB；编译期间空闲内存约 6 MB，zram 换出 112 MB |
| 闪存 | 读 329 MB，写 427 MB |
| 产物 | odex 105 MB、vdex 71 MB；**没有应用镜像**（installd 只在按画像编译时生成） |
| 没有应用镜像的影响 | 冷启动轮流各 3 次：有 17.6/17.2/18.4 s，无 18.5/18.0/17.8 s，均值差约 0.4 s，在波动之内。不为此改 installd |

另几次全量编译在 1214–1410 s 之间，同一量级。

## PackageManager 的看门狗和编译唤醒锁

读 8.1 源码确认：
- 安装在 PackageManagerService 的处理线程上进行（`processPendingInstall` → `installPackageLI`），编译也在这个线程里（`performDexOpt`，`REASON_INSTALL`）。
- 看门狗给这个线程的时限是 `WATCHDOG_TIMEOUT` = 10 分钟（`Watchdog.addThread(mHandler, WATCHDOG_TIMEOUT)`）。超时就杀掉 system_server，即整个界面重启，安装失败。
- 每次编译期间持有的唤醒锁（`PackageDexOptimizer.performDexOpt`）时限是同一值加 1 分钟。安装、`cmd package compile` 和后台作业的编译都经过这里。

AOSP 的注释说，这个线程上会有"很长的 I/O"，所以时限给到 10 分钟；手机上编译一个应用以秒计。本机以 `speed` 编译微信读书要 20 分钟：安装时如果用 `speed`，按官方步骤安装会在第 10 分钟重启。安装改用 `quicken` 之后，微信读书的安装碰不到这个时限；后台作业那次约 20 分钟的 `speed` 编译仍持有同一个唤醒锁。
- 看门狗这一条是读源码得出的，没有在真机上触发过：触发它就要让框架重启。
- 前面那 1199 s 用的是 `cmd package compile`。它在 binder 线程上编译，不受这个看门狗管。
- 唤醒锁那一半在真机上看到过：那次 1199 s 的编译结束时，system_server 记了一条 wtf：`WakeLock *dexopt* time out. Operation took 1198928 ms.`（`PackageDexOptimizer.releaseWakeLockLI`）。也就是说，唤醒锁在第 11 分钟就失效了；那次是连着电脑，设备没睡，否则后半段编译可能随休眠暂停。

## 放宽时限：0035

**frameworks/base 0035**：`WATCHDOG_TIMEOUT` 乘以 `ro.hw_timeout_multiplier`。
- 这台机器上是 4，即 40 分钟；唤醒锁随之为 41 分钟，盖得住一次约 20 分钟的 `speed` 编译。
- 这个倍数是 frameworks/base 0012 引入、给慢硬件放宽各类期限的同一个产品参数，名字和含义取自后来 Android 的 `Build.HW_TIMEOUT_MULTIPLIER`。
- 只改 `services.jar`，启动镜像不变。

**代价**：PackageManager 处理线程真卡死时，要 40 分钟才会被发现（原来 10 分钟）。这个线程上本来就有分钟级的正当工作，手机上 10 分钟的设定也只是"足够长"。
- 处理线程上的一次编译超过 20 分钟（40 分钟的一半）时，看门狗会把各线程的调用栈写进 `/data/anr/traces.txt`，只是记录，不会中止。

**余量**：
- 40 分钟约够以 `speed` 编 140 MB dex；微信读书 70.5 MB 用 20 分钟。
- 本机日常的其他应用（EinkBro、输入法、系统应用）都小一个数量级以上。

## 考虑过、没采用的

| 做法 | 为什么不用 |
|---|---|
| 安装时就编 `speed` | 安装要 20 分钟，期间设备基本不能用，还会撞上处理线程的看门狗；换来的冷启动只快约 3.9 s。同样的机器码由后台作业在设备空闲时编出来 |
| 安装时编 `speed-profile` | 第一次安装没有画像，结果和 `quicken` 一样（dex 照样快速化），耗时却是两倍半：同一台设备上 147 s 对 62 s，odex 都是 1,057,192 字节（frameworks/base 0051 的实测） |
| 后台编到 `speed-profile`（AOSP 的默认） | 打开一本书 95.6 s 对 51.4 s：打开书要跑的那些方法不在画像里 |
| 把编译挪出 PackageManager 的处理线程 | 要改安装流程本身（安装锁、冻结应用、安装结果的回调顺序都绑在这个线程上），改动大；放宽时限已经够用 |
| 给 installd 加应用镜像 | 实测只差约 0.4 s，在波动之内 |

## 使用者会看到什么

- 安装界面上方是应用名，中间是进度条和"正在安装..."。进度条只跟踪把安装包拷进会话的那一段，之后 PackageManager 编译时画面不动（微信读书 72–93 s）。全局动画已关，不额外占 CPU。
- **PackageInstaller 0001、0002**：PackageManager 拿到安装包 10 秒后还没装完，进度条下的那行字换成
  > 正在为本机准备应用…
  > 较大的应用可能要几分钟。
  - 10 秒的依据：等待超过约 10 秒，注意力就留不住，界面应当说明要等多久（Nielsen，*Usability Engineering*，1993 的三个响应时间界限）。10 秒内装完的应用看不到这行。
  - 写"几分钟"而不写实测的秒数：那个数只属于微信读书一个应用，屏幕上写一个下一个应用做不到的数，不如给出数量级。
  - 只换原有那一行的文字，不加控件、不针对某个应用；新字符串只写默认（英文）和简体中文。
- 编译那一两分钟 CPU 占满，别的应用会慢。
- 之后编到 `speed` 在设备空闲时进行，界面上没有提示；编完之前，应用一直用它已有的代码。
- 尚未在真机上验证：从"文件"打开安装包的整条手动路径，包括那行提示何时出现、装完的图标是否落在第一屏的空格子里。

## 微信读书自动安装：调研与方案

2026-10-16 定下的方向：发行物里不带微信读书；系统从腾讯官方地址现场下载，核对是腾讯签名后自动装好，使用者不用多做一步。手动安装（上文腾讯的官方步骤）照旧可用。

### 为什么不打包

微信读书是腾讯的闭源应用。把安装包放进公开发布的镜像，等于在 GitHub 上再分发它；没有授权就有被下架的风险。现场从腾讯官方地址下载，我们不经手安装包的内容。

### 官方地址（2026-10-16 查得）

腾讯的墨水屏版安装指引（https://ink.qq.com/ink/guide）上的"点击下载微信读书墨水屏版安装包"，读页面脚本得到的地址是 `/web/download_ink`：

| 步 | 地址 | 结果 |
|---|---|---|
| 1 | `https://ink.qq.com/web/download_ink` | 302 → `https://weread.qq.com/download?p=105&c=900` |
| 2 | `https://weread.qq.com/download?p=105&c=900` | 302 → `https://download.weread.qq.com/pkg/105/releases/2.1.2.10245900_900.apk` |
| 3 | `download.weread.qq.com` | 302 → 腾讯的 CDN；`application/vnd.android.package-archive`，127,467,642 字节，2026-06-23 |

- 入口地址固定，指向当前版本，所以装到的总是腾讯当时发布的版本，不用我们跟着改。
- 这次取到的是 2.1.2（versionCode 10245900），与测试机上装的大小相同。
- 第 2 步对 HEAD 请求返回 404，要用 GET。
- 腾讯的指引页还列了"Kindle"一栏，写的是原厂 Kindle 不能装第三方应用，请用网页版 `r.qq.com`。

### 怎么核对

APK 只有 v2 签名（没有 `META-INF/*.RSA`）。签名证书 SHA-256：

```
e4dd2f049941989ffafa45aef52eda9701372c27bc1708e89c217935140bfa1c
```

由测试机上装的 2.1.2 读出。Android 要求同一应用的更新用同一证书，所以这个值跟版本无关。核对两件事：包名是 `com.tencent.weread.eink`；签名证书等于上面的值。签名本身是否完整，由 PackageManager 解析安装包时验证（`PackageParser.collectCertificates`）。

### 在哪一侧做

| | Kindle 原厂系统里由安装器下载 | Android 首次联网后自己下载 |
|---|---|---|
| 网络 | 原厂已配好 Wi‑Fi | 要先在 Android 里连 Wi‑Fi；用微信读书本来也要联网登录 |
| 核对签名 | 原厂系统里要自己解析 v2 签名块，完整性验证做不到 | PackageManager 原生完成 |
| 存放 | FAT 用户区多占 122 MB；Android 里 FAT 只读、只有 root 能读，还要另想办法拿进来 | 应用自己的目录 |
| 以后重装 | 不能 | 能 |

**采用：Android 侧。** 签名核对和安装都是 Android 的原生能力，不在原厂系统里重做一套。

### 方案

一个很小的系统应用（暂名 Readom 应用安装），带 `INSTALL_PACKAGES`（特权权限，加进 `privapp-permissions`）：

1. 开机完成、网络连上时检查：微信读书没装，且没有被使用者卸载过（只装一次，卸载后不再自动装）。
2. 从 `https://ink.qq.com/web/download_ink` 下载（跟随跳转；断网后续传），通知栏显示进度。
3. 核对包名和签名证书；不符就删除并在通知里说明，不安装。
4. 用 PackageInstaller 会话安装，不弹确认。安装时的编译级别是 `quicken`，本机一两分钟，通知栏写明"正在为这台设备准备它的代码，一两分钟"。
5. 装完删除安装包。

装完之后编到 `speed` 那一步和手动安装的应用一样，由后台作业在设备空闲时完成（见"装的时候编译什么"）。

**证书链（2026-10-19 核对）**：跳转链上四个主机——`ink.qq.com`、`weread.qq.com`、`download.weread.qq.com`，以及最终那台 `*.dlied1.cdntips.net` 的 CDN——的证书**全部上溯到同一个根：DigiCert Global Root G2**。这个根在本项目镜像的系统根证书库里（`/system/etc/security/cacerts/c90bc37d.0`，共 143 个根）。也就是说这条下载链在设备上能通过校验，不需要自带证书，也不需要往根证书库里加东西。当天取到的仍是 2.1.2（versionCode 10245900）。

### 实现

`device/amazon/pw3/apps/WeReadInstaller`，包名 `org.readom.wereadinstaller`，特权应用（`privapp-permissions-wereadinstaller.xml` 授予 `INSTALL_PACKAGES`）。

- **时机**：开机完成后排一个 JobScheduler 任务，条件是"有网络"，持久化、按指数退避重试（首次 10 分钟）。网络断开或任务超时时，已下载的部分保留，下次续传。
- **只自动装一次**：看到微信读书已安装（无论是本应用装的还是手动装的）就记为完成，以后不再自己动作；使用者卸载之后**不会**被自动装回来。下载期间使用者手动装好了，也直接作废这次下载。
- **入口跟着微信读书在不在走**：装好之后入口组件被禁用，首页和"全部应用"里都没有它。微信读书被卸载后入口重新启用（`StatusActivity.followWhetherWeReadIsInstalled`），回到"全部应用"里（不回首页——那一格已经交接给微信读书），因为这台机器要能不用电脑就把它装回来。两处核对同一件事：卸载当场（`RemovalReceiver`，接 `PACKAGE_FULLY_REMOVED`——这是 API 26 以后清单声明的接收器还收得到的那几条之一，`PACKAGE_REMOVED` 不是），以及每次开机（`BootReceiver`，兜住 `pm uninstall -k` 那种两条广播都不发的情形）。**自动下载不会因此重新开始**：只有使用者点"现在下载"才会。
- **续传**：记下 ETag 和总长度，续传时带 `Range` 和 `If-Range`。腾讯的 CDN 支持分段（206）并给 ETag；版本变了服务器会返回完整文件，从头下载。CDN 的最终地址里带客户端 IP，不保存，每次都从官方入口重新跳转。实测跳转链全部是 HTTPS：`ink.qq.com` → `weread.qq.com` → `download.weread.qq.com` → 腾讯 CDN。
- **核对**：`getPackageArchiveInfo(GET_SIGNATURES)` 解析并验证签名（含 v2），包名必须是 `com.tencent.weread.eink`，并且只有一个证书、SHA-256 等于上面的值。不符就删除，3 次后不再自动安装，并在通知里说明。
- **安装**：PackageInstaller 会话 `MODE_FULL_INSTALL`，提交后由系统完成（一两分钟），通知栏写明。重启打断的会话会被放弃并重试。成功后删除安装包。之后设备空闲时，后台作业把它编到 `speed`。
- **通知**：一个低优先级通道，下载进度最多 5 秒更新一次（墨水屏每更新一次就要刷一次屏）。文字中英两份。
- **并发与接续，三条不变式**（2026-10-30 Codex 第三到七轮查出来的问题都落在这三条上，写下来是因为下一个改这段代码的人会再碰一次）：
  1. **一个进程里同时只有一次尝试在跑。**一把进程级的锁（`Installer.BUSY`）在整个 `run()` 期间持有，拿不到就等 30 秒、还拿不到就把这次让给重试。否则"现在下载"取消旧任务、立刻排新任务时，旧任务要等自己轮询到取消标志才退出，两次尝试会同时打开并截断同一个文件。拿到锁之后还要再查一次取消标志：等的那 30 秒里，要它的那一方可能已经不要了。
  2. **提交了安装会话，队列里就一定已经有重试。**`attempt()` 在 `install()` 成功之后、以及发现会话还活着时，都返回 `RETRY`，于是 job 在放手之前先把重试排进去。`install()` 只有一个调用方，所以任何被提交的会话都来自一次 job 运行——不论安装结果的回调和工作线程谁先跑，重试都不会丢。**不要改成"读一个标记再决定要不要排"**：那种形状看着等价，实际上在"读完"和"旧任务被移除"之间留了一个窗口，标记留着却没有 job 来消费，而通知已经许下了"稍后会自动重试"。代价是每次安装多一次 job 运行，而那次在 `finished()` 处立刻结束。
  3. **记下的长度和 ETag 描述 `apk()` 那个文件，文件在它们就在、文件走它们才清。**长度同时是"已经下完了"的判据，所以下载成功之后**不能**清掉它——清了，一次在最后一个字节和安装之间被取消的尝试就会回来面对一个认不出来的完整文件，重新请求整份并在 200 上把它截断。要换成另一个对象时，先**同步**（`commit()`，不是 `apply()`）让旧长度失效再替换文件：`apply()` 在后台写、而且可以跳过被后来覆盖的中间版本，所以"先清"不构成盘上的屏障——强杀之后可能回到旧长度正好等于新对象前缀的局面，把前缀当成下完的包，验签失败还白消耗一次"三次拒绝"额度。

真机实测（2026-10-23，在没有装过微信读书的系统上）：开机后 11 秒任务启动；下载并写入会话约 100 秒，编译 124.7 秒，合计 3 分 48 秒；首页那一格随即交接给微信读书。之后连开三次，冷启动 26.7 / 13.0 / 6.6 秒，没有一次无响应。

### 下载器把自己那一格交给微信读书

**要解决的**：下载器那一格在微信读书装好之后应当变成微信读书——**在原来那一格**，哪怕使用者已经把它挪到别处；下载器自己随即消失。

**曾考虑、没有采用的做法**：在系统的默认布局里直接写上微信读书的包名（`<resolve>`：装了就放它，没装就放下载器）。它能工作，但错在根上：**布局是镜像的，镜像没有理由知道使用者会装哪些应用**，而要求是系统层面不为某一个应用写特殊逻辑。这种东西也没法只做一半：一旦布局里躺着一个包名，下一个包名就只是"要不要再加一个"的争论，不是原则。

**现在的做法**：这件事只有下载器知道，所以由下载器做。它在装成功、准备下架的那一刻，更新启动器桌面表里**自己那一行**，把它指向装好的应用；行里的 `container`/`screen`/`cellX`/`cellY` 一个字没动，所以替换就发生在那一格。然后才禁用自己的组件。

能这样做，靠的是启动器**自己公开的接口**，四件事都在构建出来的 APK 上核对过：

| 事实 | 核对方式 |
|---|---|
| 桌面表是导出的 provider，`com.android.launcher3.settings/favorites` | `aapt d xmltree` 读发行 APK 的 manifest |
| 读权限 `normal`、写权限 `signatureOrSystem` | 同上；下载器与启动器都不设 `LOCAL_CERTIFICATE`，同一把发行密钥签，且都是特权应用，两条路都通 |
| 外部写入会让启动器重载 | `LauncherProvider.update()` 调 `reloadLauncherIfExternal()`（AOSP 自己为此留的） |
| SELinux 允许应用之间互调 | `system/sepolicy/private/app.te`：`binder_call(appdomain, appdomain)` |

**行里不写标题和图标**（`title`/`icon`/`iconPackage`/`iconResource` 置空）：`itemType` 改成"应用"之后，启动器每次加载都从包里读名字和图标，所以微信读书改了图标或名字也会跟着变。

**和"装完的应用出现在首页"那条路撞车怎么办**：系统那条路（会话写明是人要装的 → `SessionCommitReceiver`）可能已经在别处放了一个图标，先后顺序不由我们定。所以交接是：先更新自己那一行，**成功之后**再删掉其它指向同一个应用的行。顺序反过来的话，一旦更新失败就会把唯一的图标删掉。

**做不到就什么都不做**：换了别的启动器、使用者把下载器那一格从桌面上移掉了（这时系统那条路放的那个是唯一的图标，删不得）、应用没有可启动的界面——三种情况都只记一条日志，桌面保持原样，下载器照样下架，因为微信读书确实已经装上了。

**换了默认布局之后**：这一行不会再消失。改布局不再清桌面表（`aosp-launcher3/0015`，见 `known-issues.md` 第六节），所以交接过的那一格一直是微信读书。那一格交接走之后，布局里"下载器那一格"就不在桌面上了——下一次改布局推版本号时，差集按理会把它补回来。**微信读书还在的时候不会补**，而且靠的不是特例：入口组件此时是禁用的，而布局解析器（`AutoInstallsLayout.AppShortcutParser`）用 `getActivityInfo(cn, 0)` 查这个组件——flags 为 0 时禁用的组件查不到，于是抛 `NameNotFoundException`，换规范包名再查一次还是抛，记一句 `Favorite not found` 后放弃这一条。所以**下架必须真的禁用组件**，不只是把界面藏起来；否则改一次布局就会多出一个下载器图标。反过来，微信读书被卸掉之后入口会重新启用（上面那条），这时改布局确实会把下载器那一格补回首页——那也正是该有的样子。

### 装完的应用出现在首页

**要什么**：使用者自己装的应用，装完就出现在首页上。这跟上一节是两件事：上一节是"下载器那一格变成它装的东西"，这一节是**其它所有应用**落在哪儿。两节都不认识任何具体包名。

这件事有两道门，缺一道就看不到图标。

**第一道：谁有资格上桌面。** 装完之后 `PackageManagerService.sendPackageAddedForUser` 会给默认桌面发一条会话广播，里面带着这次安装的 `installReason`；Launcher3 的 `SessionCommitReceiver` 只对 `INSTALL_REASON_USER` 排队加图标，别的直接返回。而 AOSP 自己的 PackageInstaller 界面**从不设这个字段**，默认是 `INSTALL_REASON_UNKNOWN`——所以在原版上，从文件管理器点开一个 APK 装完，桌面上什么都不会多（开发期间实测）。`aosp-packageinstaller/0003` 在 `InstallInstalling.onCreate` 里补上这一行：这台机器上点开 APK 的就是机器的主人，没有第二种可能。

**第二道：放哪一格。** AOSP 的 `AddWorkspaceItemsTask` 从屏幕索引 **1** 开始找空格子，第 0 屏永远不给。手机上这是对的：有好几屏，第 0 屏是搜索框和小部件那一屏。本机只有一屏（`aosp-launcher3/0012`），于是"找不到空格"→ 在末尾新建一页 → 图标放到第 2 页；而去第 2 页要横划，屏幕上没有任何东西说有第 2 页（全部应用的小箭头去掉了，`0006`；AOSP 画在页面下方那条线在滚动开始前 alpha 是 0，它回应滑动而不是邀请滑动；指示器是使用者明确要求去掉的）。图标确实放了，人确实找不到。`aosp-launcher3/0016` 把搜索改成从第 0 屏开始：第一屏 4×4，第 0 行是搜索框，其余 12 格里布局占 5 格、还空 7 格，满了才往后面的屏幕找，全满了才新建一页——后两步和 AOSP 一样。

**第 0 行要标成占用**：搜索框不是桌面表里的行。`LoaderCursor` 读桌面时会把第一屏第 0 行标成占用，所以放位时也必须标；不标的话第一个装的应用会被写进搜索框后面那一格，然后在下次加载时被丢掉而不是显示出来——AOSP 不会碰到这个问题，因为它从来不往这一屏放东西。

**启动器没在前台的时候装完也不会漏**：这条路排的队在启动器下次显示时冲掉（`InstallShortcutReceiver`），这也是 AOSP 自己的设计。
