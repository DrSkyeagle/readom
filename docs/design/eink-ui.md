# 墨水屏界面规范

适用于本项目能控制外观的所有界面：framework 的默认主题（对话框、弹出菜单、提示条；没有自定主题的第三方应用也用它）、系统界面（SystemUI）、设置、桌面（Launcher3）。

PW3 的条件：6 英寸 Carta 墨水屏，1072×1448，300 ppi，16 级灰；没有 GPU，系统界面软件绘制；density 1.875（1 dp = 1.875 px = 0.159 mm）。

## 一句话

**靠线条和留白分层，不靠阴影、明暗和颜色；会变化的东西尽量只动纯黑白像素；大区域的变化一步到位，不做中间帧。**

## 规则

| # | 规则 | 数值 | 依据 |
|---|---|---|---|
| 1 | 底色白，正文黑 | 底色取面板第 15 级（`#FFFFFF`），正文第 0 级 | 面板白态只有约 42% 反射率，底色要取最亮一级；E Ink 的 GL16 波形就是为白底稀疏内容设计的。`#F5F5F5`、`#EEEEEE` 这类浅灰在本机落到第 14 级，与白几乎分不出，不能用来区分区域 |
| 2 | 强调色用黑，状态靠形状 | 选中、开关、勾选至少用两种属性表达：填充/描边、字重、粗下划线 | Material 默认的青绿强调色在本机落到第 2 级，只是比正文略浅的深灰。WCAG 1.4.1 规定不能只靠颜色传达信息 |
| 3 | 浮在页面上的东西（对话框、菜单、提示条、卡片、搜索框）用黑色描边代替阴影 | 描边纯黑、`1dp`（本机取整为 2 px）；圆角 `4dp` | 软件绘制根本不画 elevation 阴影，白色浮层落在白底上就没有边界。描边用纯黑：灰描边对白要达到 3:1，只能用第 5 级或更深；而且 1–2 px 的细线看起来本来就比同色色块淡。宽度写成整像素，否则会出现灰色的抗锯齿边。圆角属于风格选择，没有证据支持或反对某个具体值。**一叠同层的条目不各画一个框**：描边说的是「这东西浮在页面上」，而一列条目要说的是「上一条到这里为止」，所以条目之间用一条同色同粗的横线，不是每条四条边。同一个东西浮起来的时候仍然用框——通知在面板里是一条横线，而它作为弹出通知浮在正文上时四边都描（frameworks/base 0065 按 `isPinned()` 分这两种）。2026-10-28 使用者在设备上对比过通知面板的两种画法，选了横线 |
| 4 | 对话框背后不压暗 | `backgroundDimAmount` 为 0 | 压暗 60% 会让白底变成第 2 级深灰：打开、关闭各要用 16 级波形（约 463 ms）刷一次整屏，还会留下残影。为 0 时窗口管理器根本不显示压暗层（`DimLayer` 在 alpha 为 0 时保持隐藏） |
| 5 | 不用渐变、半透明和动画 | 三项动画倍率默认 0；渐变改成纯色或去掉 | 渐变在 16 级灰上显示成一圈圈色带。本机每一帧都是一次面板更新（A2 134 ms、DU 216 ms、16 级 463 ms），200 ms 的动画在屏上最多出一两帧带灰的中间画面 |
| 6 | 大区域的手势在手指抬起时一步生效 | 翻页、拉出面板、打开全部应用：抬手后一次画完；小区域连续控件（亮度滑块）可以跟手，但同时保留点按和步进 | 拖动时延迟超过 25 ms，操作表现就开始变差；本机最快一帧要 134 ms，大区域跟手只会产生一串没画完的画面 |
| 7 | 触控目标按位置定尺寸 | 屏幕中部的列表行 ≥ 48 dp（7.6 mm）；贴边的导航栏、工具栏 ≥ 56 dp（8.9 mm）；角落 ≥ 64 dp（10.2 mm），或与相邻目标拉开间距；间距 ≥ 8 dp | 实测研究：手指点中所需的尺寸在屏幕中央约 7 mm，边缘约 9 mm，角落约 12 mm（R95）。墨水屏上点错代价更高：错误界面要画出来（216–463 ms），返回后还要再画一次 |
| 8 | 字号与字重 | 连续阅读的界面文字 ≥ 16 sp，次要说明 ≥ 14 sp，12 sp 只用于时间、页码这类一眼看的短标签；小字只用 Regular 和 Medium | 临界字号研究（拉丁 x 高 12′，中文约大 17%），按本机 35–40 cm 的视距换算得出 |
| 9 | 大块纯黑只给静止的元素 | 会频繁出现、消失的大块深色（整行反色、深色面板）不用 | 大面积深色在出现、消失时残影更重 |

规则 3、4、5 的依据最充分。具体数值（2 px、4 dp、56 dp）是有依据的起点，还没有在本机上做对照测量，缺什么见下文「已知限制」。没有找到专门比较墨水屏界面描边粗细、圆角或触控尺寸的对照研究。依据来自一份对 38 个来源（阅读研究、显示标准、人机交互实测）的调研，调研报告没有随仓库发布。

## 数值在哪里定义

三个数值：`pw3_outline` 黑色，`pw3_outline_width` 为 1dp，`pw3_corner_radius` 为 4dp。改动时以本文为准，下列位置要一起改。

| 范围 | 位置 | 说明 |
|---|---|---|
| framework 的对话框、弹出菜单、提示条 | frameworks/base 0023：`dialog_background_material.xml`、`popup_background_material.xml`、`toast_frame.xml` 里直接写数值；0054 在全屏提示浮层的布局里直接写它底边那条线 | 见下方说明 |
| SystemUI | frameworks/base 0024：`packages/SystemUI/res/values/pw3_eink.xml` | 任务管理卡片、“全部清除”按钮、电源菜单（0029）、通知之间那条横线（0059、0065） |
| 设置 | Settings 0004：`res/values/pw3_eink.xml` | 搜索栏、建议卡片、标题栏下的横线（0008、0009） |
| 安装器（PackageInstaller） | PackageInstaller 0004：`res/values/pw3_eink.xml` | 每屏顶栏下的横线（0004、0005）；只有颜色和线宽，没有圆角 |
| 桌面 | Launcher3 0007：`res/values/pw3_eink.xml` | 主屏搜索框；编辑模式的页面描边（0008，另有加倍的 `pw3_outline_width_double`） |
| 微信读书下载器 | `device/amazon/pw3/apps/WeReadInstaller/res/drawable/outlined_button.xml` 里直接写数值 | 按钮 |

**横线的 inset 按整像素写。**标题栏下的横线是一个 layer-list：底层黑，上层的底色在底边让出一个线宽。inset 经 `getDimensionPixelOffset()` 读取、向下取整，1dp × 1.875 只得 1 px；描边（`<stroke>`）经 `getDimensionPixelSize()` 四舍五入，得 2 px。所以 Settings 和 PackageInstaller 另有一个 `pw3_rule_inset`，直接写 `2px`（本机只有一种密度）。

**为什么 framework 不新增一个统一的资源**：往 framework-res 加新资源名会改变资源 ID（它用 aapt2 按名字排序分配），进而改变 framework.jar 和启动镜像。启动镜像一变，`/data` 里所有应用的机器码都要重编，否则微信读书等应用会退回解释执行（开发期间实测，这时打开一本书要 53.7 s）。所以 framework 只改已有资源的值，各应用里各存一份同样的数值。Launcher3 用公开 SDK 编译，本来也无法引用 framework 的私有资源。

同样的原因，**覆盖或修改 framework 资源时，条目正上方的注释要逐字保留 AOSP 原文**，PW3 的说明写在 `<resources>` 外的文件头里。aapt2 会把紧挨在条目上方的注释抄进 `com.android.internal.R` 作为 Javadoc；注释行数一变，framework.jar 里的行号就变，启动镜像也随之改变。开发期间试过覆盖导航栏高度：即使注释照抄 AOSP，生成的 R.java 在这个条目处仍少了一行，启动镜像随之改变，所以导航栏高度没有改。原因推断是：该资源在 `values-sw900dp` 里还有一份带注释的定义，覆盖后那份注释没有再出现在 R.java 里；没有逐行核实 aapt2 的合并过程。

**注释会改变启动镜像，这一点有实测。**补丁 0060 只改 `core/res/res/values/colors.xml` 里 `notification_action_list` 一个值，它的第一版在条目正上方放了 7 行 PW3 说明。对照的是导出回执 `build-result.json` 里的 `boot_image.sha256`（45 个启动镜像文件的哈希；载荷清单里的 `boot_image_sha256` 就是它，安装器据此判断升级后要不要重编应用）：

| 构建 | `boot_image.sha256` |
|---|---|
| 0060 之前连续七次构建 | `73db7fc9d00b36b16b0295034c2c0f49eccf92683a33ee4058c0c6d92123c3d4` |
| 0060 第一版，条目上方带 7 行注释 | `ba857c7b91108dd45674ae86ca31eac65f6127a56a3abff4bb5ec1672086ccfc` |
| 注释挪进补丁头部后（重建三次） | `73db7fc9…`，与之前相同 |

值的改动本身不进启动镜像（值在 resources.arsc 里），变的是注释下方那些类在生成的 `R.java` 里的行号，而行号在 framework.jar 里。所以框架资源改动落地前要做的事只有一件：构建完比对这个字段。

## 对流畅和性能的影响

| 改动 | 影响 | 依据 |
|---|---|---|
| framework 只改资源值 | 启动镜像不变，应用机器码仍然有效 | 开发期间核对过：只改资源值的构建前后，45 个启动镜像文件逐字节相同 |
| 不压暗 | 更快：每次打开、关闭对话框各省一次整屏 16 级刷新，也不再走 CPU 压暗合成 | `DimLayerController` 在 dimAmount 为 0 时不调用 `show()` |
| 描边 | 可以忽略：每个浮层多画一条矩形路径 | 软件 Skia 绘制，只在浮层出现时画一次 |
| 任务管理 6 张卡片 | 首次打开最多多读 3 个图标（原来显示 3 张卡片的标题栏图标）；不滚动，翻看任务不再触发面板刷新 | 仍然没有任务预览图；图标来自任务加载器原有的缓存 |
| 桌面上滑 | 更少：滑动过程中不重绘，抬手后只刷新一次 | 动画倍率为 0，过渡在第一帧结束 |

上表的影响由代码推得。设置、任务管理的启动耗时，以及打开对话框、桌面上滑时内核日志里的刷新区域和波形，尚未在真机上测量。

## 已知限制

- 描边宽度和分隔线灰级没有在本机上做对照：2 px 还是 3 px（对话框这类顶层窗口另看 3 px）、分隔线用哪一级灰，缺同一张测试图在面板上的实拍对比。
- 黑描边浮层反复开关后的残影没有专门测过。窗口出现或消失时，显示服务已在它占的区域用一次 GC16 重画（`device/amazon/pw3/epdc/Panel.h` 的 `replaced()`），代价是那块区域闪一下。
- 按下反馈没有测过：动画倍率为 0 时框架默认的水波纹还看不看得见，改成按钮内侧加黑框是否更快，缺慢动作拍摄（240 fps）和内核日志的对照。
- 规则 7 的三档触控尺寸来自文献，本机的触摸精度没有测过。导航栏仍是 AOSP 的 48 dp，不是规则 7 要的 56 dp；改它要覆盖 framework 资源 `navigation_bar_height`，会改变启动镜像（见「数值在哪里定义」），也就是让 `/data` 里所有应用重编一次。
- 规则 8 的字号下限由文献换算得出，本机上的最小可用字号没有测过。
- 各灰级在面板上的实际明度没有用 RAW 照片测过，调色板该用哪几级还没定。因此几处小面积的灰没有改：进度条轨道灰 219（第 13 级）、快捷设置亮度滑块轨道灰 229、应用页和文件页里的灰 224、AOSP 次要文字灰 117（`secondary_text_material_light` 即 `#8a000000` 落在白上），每处只占所在区块的 0.4%–5.7%。
- 使用 AppCompat 主题的界面不受 frameworks/base 0062 影响：支持库自带一份同名的 `primary_material_light`（`frameworks/support/v7/appcompat/res/values/colors_material.xml:29`，仍指向 `material_grey_100`），`Theme.AppCompat.Light` 用的是它。系统自带的界面按区块复测，没有发现这种情况。
- 第三方应用给自己的通知设的颜色（`Notification.color`）没有改：AOSP 只把它调到对白底至少 4.5:1，不强制成黑，而规则 2 要求黑。系统通知已是黑（frameworks/base 0061）；第三方应用的通知在本机上没有量过。
- 设置和全部应用的列表仍是连续滚动，按规则 6 改成整页翻页没有实现。
- 任务管理只显示最新的 6 个任务，更早的看不到，只能用“全部清除”一并移除。
