# 诊断与启动失败的出路

本文讲两件事：发行版出了问题时，证据（报告区和日志文件夹）怎么从设备交到人手里；Android 启动失败时，设备怎么自己回到原厂系统，启动画面又怎么把这条出路告诉使用者。

## 要解决什么

发行版出问题时，如果没有专门的通道，就**没有任何证据可取**：

- 使用者手里没有 adb。`user` 构建按设计就不开 adb（`release-build.md`），`userdebug` 上 adb 也可能正好坏掉——开发期间就遇到过插线之后 USB 总线上什么都没有的情况，连"为什么没有"都读不到。
- 内核日志环形缓冲只有 32 KB（`log_pos_goal=0x8fff0000`，与原厂共用）。用上几小时之后，开机那段早被覆盖：开发期间有一次取到的 `previous-kernel.txt` 只剩 3 行，全是 PMIC 的。
- 用户空间的状态（`sys.usb.config`、`init.svc.adbd`、`sys.pw3.init_error`、刷新计数、内存）根本不在内核日志里，采样程序 `pw3-boot-report` 也不往内核日志里打它们，只写进下文的报告区。

要的东西很具体：**普通使用者插上线、把 `android/logs/<时间>/` 整个发出来，里面就有上一次 Android 启动的状态。** 使用者不需要懂任何东西。

## 三条路，两条否掉

### 否：原厂侧 loop 挂载数据镜像

最省事的写法是启动器（跑在原厂内核下，root）`mount -o ro,noload -o loop android/data.img`，直接读 Android 写在 `/data` 里的文件。**原厂内核不支持 ext4**：

```
CONFIG_BLK_DEV_LOOP=y
CONFIG_EXT2_FS=y
CONFIG_EXT3_FS=y
（没有 CONFIG_EXT4_FS）
```

（证据：本机 `/proc/config.gz`，555 个配置项。）数据镜像是 `make_ext4fs` 造的、带 extents 的 ext4，ext3 驱动看到 `INCOMPAT_EXTENTS` 会直接拒绝。所以这条路在原厂内核上不成立。

### 否：Android 把 FAT 用户区挂成读写，写一个文件

Android 这边有 vfat，技术上可以挂 `mmcblk0p4` 写文件。否掉的理由是**风险落在最不能出事的那个分区上**：系统镜像和数据镜像就是这个 FAT 分区里的两个文件。多一个内核、多一次 FAT 元数据写入，就多一种"Android 被拔电时留下悬空簇链"的可能；之后原厂系统的 `dosfsck` 去"修"它，修到的是放着镜像的那张表。为一份诊断文本换这个风险，不值。

### 做：预先分配好的固定大小报告区

把报告区做成**一个尺寸永不变化的普通文件**，让 Android 只写它自己的扇区，FAT 的任何结构都不碰：

1. **安装器创建** `android/report.bin`，64 KB（`install.c` 的 `ensure_report_area`）。写进去的是一份占位报告——正文只有 `installer_made=1`，其余补零——整 64 KB 一次写满，和镜像一样完整分配、不稀疏。用占位报告而不用全零，是为了让这个文件凭自己的字节就认得出是本项目的：全零的区翻掉一个字节，安装器和 preinit 就都不再认它；一份报告即使魔数坏了，首行仍能解析、正文校验和仍对得上，还认得出来，可以重做（`pw3_report_damaged_magic`）。每次点击都检查：没有就建，尺寸不对或魔数坏了就重建。理由有两条——装过旧版本的设备要补上一个；有人从电脑上删掉或截断了它，preinit 会按 extents 把它映射短，于是 Android 会写进已经不属于它的簇。它是诊断，所以对一切让路（`installer` 测试覆盖下面三条）：

    - **建不出来就不建**，只写一行日志、照常安装。
    - **不覆盖不是我们的文件。** `android/` 是安装器的文件夹，但这是"拥有它写的那五个名字"的理由，不是"名字对得上就覆盖第六个文件"的理由。尺寸不对时先看文件本身，两种才算我们的：开头是魔数的（Android 写过报告、之后被电脑截断或加长；比魔数还短的文件，只要是魔数的开头一段也算，那是写到一半或被截断的），以及不长于一个报告区、每个字节都是零的（包括零字节文件）。是每个字节而不是开头几个——开头是零、后面是别人数据的文件就是别人的数据；代价最多读 64 KB，因为比报告区还长的文件不可能是"从没写过"的那一个。别的原样留下，并在日志里说清楚。读不出来的也不算——"不知道"正是这条规则存在的场合。
    - **不花掉用户存储的最后一点空间。** 这条路径是"没有东西要装"的那条，根本没做空间检查；而这次点击自己的日志是在它之后写的，并且那些写入是必须成功的（`helper.c` 的 `write_result` 用的是 `require`）。所以要求存储在报告区之后还剩 1 MB 以上，否则不建。门槛不取安装器的 64 MB 保留额：剩 64 MB 的存储并不需要扣着报告区不给。
2. **preinit 映射它的扇区**：新内核里的 PID 1（preinit）按簇用 FIBMAP 把 `system.img`、`data.img` 的 extents 量出来、校验不交叉（`preinit/TestFileMapper.h`、`FatCrossLink.h`，`fat-cross-link` 测试）。报告区是第三个 `pw3_file_mapping`，同一套校验、同一套"FAT 保持只读"，映射成 `dm-3`（`preinit/TestFileInit.h`）。只有尺寸正好 64 KB、开头是魔数或全零的文件才会被映射；量不出它的簇、或建不出映射，只是这次启动不写报告，不影响启动；与镜像交叉或被 FAT 上别的文件占用的簇则会让整个启动被拒绝。
3. **Android 写它**：oneshot 服务 `pw3-boot-report` 在 `sys.pw3.storage_ready=1` 时启动，不等 `sys.boot_completed`——没能走完的那次启动才最需要报告。它在两分钟里采样四轮，最后把整个 64 KB 一次写进 `/dev/block/dm-3`（`initcheck/BootReport.cpp`、`initcheck/pw3-boot-report.rc`）。写的是固定字段，加上几个系统组件在 logcat 里各报了几条警告（只记组件名和条数，不抄日志原文，见下文"报告里写什么"）；不读 `/data` 里的任何路径名。写成没写成，都在内核日志里用 `pw3-report-area:` 标签说一句。

    PID 1 也写它，但只在它**拒绝启动**的时候：`stop()` 把已经组好的那一行（含这次启动第一个失败的系统调用）写进去（`preinit/PreInit.c` 的 `report_stop`，写入本身在 `report/ReportStop.h`），字段名 `preinit_stopped=`，名字定在两侧共用的头文件里。写在 120 秒等待**之前**，所以拔电的人也拿得到。映射之前的那些 `stop()` 没地方写就不写——能让下一次点击做出反应的两个拒绝（系统镜像哈希不符、系统镜像超级块不对）都在映射之后。
4. **下一次启动器取出来**：报告区是 FAT 里一个普通文件，启动器照常读，放进 `android/logs/<时间>/android-report.txt`，和内核日志同一个目录（`helper.c` 的 `save_android_report`，紧跟上一次的内核日志之后）。筛查用 `pw3_report_keep`：内核日志那套允许列表判断的是"这行是谁打的"，而报告的每一行都由采样程序或 PID 1 写出，那一道在这里没有东西可判断；留下的是第二道闸——标识符检查（MAC、连续 12 位以上的十六进制串、`ssid`/`serial`/`command line`），它正是为"没人预料到的那一行"写的。文件的头尾各一行 `pw3-android-report-v1`，带启动序号、长度和两个计数，形状与过滤过的内核日志一致，打开文件的人一眼就知道它被筛过、筛掉了多少。

    和安装器一侧同样的让路规则：这一份拷贝也是"顺手留下的"，而这次点击自己必须写成的那些文件排在它后面，所以写之前先问存储还剩多少（`pw3_store_has_room`：要求减掉它之后还剩 1 MB 以上），不够就跳过。上一次的内核日志 `previous-kernel.txt` 用的是同一条规则——两者的失效方式完全一样：一个顺手文件把最后的空间用掉，然后启动死在一个必须成功的写入上。存储答不上来（`statvfs` 失败）也算没空间——不知道不可能比启动本身更重要；日志里记的是存储报出来的字节数，答不上来时记一个任何存储都不可能有的数，好让转交出去的文件夹里"这个文件为什么不在"本身也有答案。
5. **不需要回写**：启动器只读；安装器只在建区、重建时写，Android 只在启动时写，两边永远不会同时碰它。**每次点击都把当时有效的那份取一遍，不记"取过了"**。曾考虑把启动序号记进 `android/state`、取过的不再取；没有采用，因为 `android/state` 是安装器的文件，格式由安装器的测试钉住，为了省一份 64 KB 的重复拷贝就让启动器也成为它的写者，不值；而重复本身不是错误，`boot=` 说的是哪一次启动写的，两个文件夹里同一个序号就是同一份报告被读了两次，读的人分得清。

### 报告里写什么

一行一项。采样程序在服务启动后第 0、30、60、120 秒各采一轮（每轮限时 5 秒），所以同一个字段会出现多次，最后一次就是这次启动走到了哪里：

| 组 | 字段 |
|---|---|
| 每轮开头 | `snapshot=<轮次> uptime_s=<开机秒数>` |
| 这次启动 | `ro.build.version.incremental`（哪个版本写的）；启动序号在首行的 `boot=` |
| 初始化 | `sys.pw3.storage_ready`、`sys.pw3.hardware_ready`、`sys.pw3.init_error` |
| USB | `sys.pw3.usb.phase`、`sys.pw3.ffs_ready`、`sys.usb.ffs.ready`、`sys.usb.state`、`init.svc.adbd` |
| 服务与开机进度 | `init.svc.zygote`、`init.svc.surfaceflinger`、`init.svc.bootanim`、`init.svc.pw3-fg-observe`、`sys.boot_completed`、`dev.bootcomplete`、`service.bootanim.exit` |
| 内存 | `/proc/meminfo` 的 `MemFree`/`Cached`/`Buffers`/`AnonPages`/`Slab`/`SwapFree`，以及 `/proc/buddyinfo` |
| 输入 | 电源键和触摸屏的输入设备在不在 |
| 显示 | framebuffer 的几何参数、EPDC 驱动报告的刷新模式、对屏幕 16 行像素的抽样（灰阶范围、级数、哈希） |
| 系统日志 | `android_error_count`：一组固定的系统组件（SurfaceFlinger、AndroidRuntime、ActivityManager 等）各有几条警告级以上的 logcat 行，形如 `AndroidRuntime=2`。只记组件名和条数，不抄原文：原文是应用自己写的，可能带文件名或网址，而这个文件会被转交出去。组件名取自代码里的固定列表，不是设备给的字符串 |
| 收尾 | `complete`；某一轮超时则是 `stopped at the snapshot deadline` |
| 拒绝启动 | `preinit_stopped=<原因>`，只由 PID 1 写（见上文第 3 步） |

64 KB 远够四轮采样；放不下的行不写。

格式（`device/amazon/pw3/report/ReportArea.h`，两端共用一个头文件）是文本而不是结构体：两边今天都是 ARM 小端，但文本不需要就对齐和字节序达成任何约定，谁用编辑器打开都能读，而且能过和内核日志同一套筛查。第一行声明后面有什么：

```
PW3-REPORT-1 bytes=<n> crc32=<8 位十六进制> boot=<n>\n
<n 字节正文，一行一项>
```

校验和取 CRC32 而不是 SHA256，正是因为这一行会被拷进可转交的文件夹，而筛查会丢掉任何连续 12 位十六进制的行（`userlog.c`，这条规则就是为此写的）。64 KB 一次写入不保证原子，所以读的一侧校验不过就当没有报告——全零（旧版安装器建的区）同样不是报告、也不是错误；安装器写的占位报告靠正文里的 `installer_made=1` 认出来，不当作任何一次启动的报告。`boot=` 只到 32 位（42 亿次启动已经超出这台机器能做到的），因为它是报告里唯一一个会被原封不动写进可转交文件夹、而行筛查对它无话可说的值——十位十进制数不可能构成筛查要抓的那种连续十二位十六进制串。`report-area` 测试覆盖这些，包括两个 CRC32 的已知答案（好让另一侧的写者有东西可对）、正文正好填满区域、以及首行根本没有结尾。

## 为什么不是"把内核环形缓冲做大"

另一个想法是把 32 KB 的环形缓冲改大，让开机那段活到被取走。否掉：那块缓冲的地址和大小是原厂侧按固定地址读的（`log_pos_goal`），改大要同时改两边，而且**它仍然只有内核日志**——用户空间状态、刷新计数、内存这些一个字节都不会进去。报告区解决的是"内容"，不是"长度"。

## 报告区同时解决的两个问题

这两个问题的根因是同一个：**原厂侧无法知道 Android 做了什么**。没有报告区，两者都只能用启发式去猜。有了报告区，安装器每次点击先读它（`install.c` 的 `read_report`），把猜换成读。

1. **大小没变的损坏系统镜像，再点一次也修不回来。** 安装器不会每次点击都重读 512 MiB 的镜像（那要多花约 19 秒，按 576 MiB 的 20.9 秒实测外推），只按状态文件里记的哈希判断镜像是否现成。镜像内容坏了而大小不变时，状态文件仍然判定 `system=ready`，安装器照常交接；preinit 拒绝这个镜像（`pw3-preinit: test system image SHA256 rejected`），约两分钟后重启回原厂。没有报告区时，再点一次只会重复同一条路——**使用者只看到启动画面，没有任何错误码，唯一的出路是接电脑删掉 `system.img`**，而这正是"只会插数据线的人"做不到的。现在 preinit 把拒绝原因写进报告区；下一次点击读到一份序号与已处理过的不同、原因是系统镜像哈希不符或超级块不对的报告，就抹掉 `system=ready`，先显示一屏说明（`PW3_SCREEN_REPAIR`）再重装系统镜像，数据镜像不动。镜像只是没读完（`could not be read through`）时不重装：那说明不了内容坏了，重读一次就够。没有报告区时，要区分"这次的拒绝"和"上次留下的"只能扫内核环形缓冲里的那行字、再加上缓冲内容的哈希，是启发式，所以不那样做。
2. **升级后的"还在编译"提示，不能按点击次数耗尽。** 换了启动镜像的升级，第一次启动要重新编译 `/data` 里的应用。如果提示只在装完后的前三次点击显示，而这三次都在编译完成前被打断，第四次就只显示普通的那一屏，而它不提编译，设备却还在编译——使用者无从知道这次为什么格外久。（那一屏在 2026-10-30 之前更糟：它写着"十分钟没出来就按住电源键"，等于在编译中途教人强制重启。现在它不写时长，只写"不要强制重启"，所以这里要补的只是"为什么久"。）所以状态文件记的是 `compiling=1`，不按点击次数递减，只在读到能证明编译做完的报告时清掉：报告里最后一次采样到 `sys.boot_completed=1`（编译在 `SystemServer.startOtherServices()` 的 `updatePackagesIfNeeded()` 里，`systemReady()` 在同一个函数里晚 700 多行，所以 `boot_completed` 必然在编译之后），`ro.build.version.incremental` 等于本入口安装的版本，而且这份报告是这次安装之后写的（安装器建区时种下的序号就是下限）。没有参考画像的应用按 quicken 编译，每个应用 60–93 秒（全量编译要 1214 秒），所以"还在编译"的窗口是分钟量级。

## 真机验证

- 已在真机上验证：Android 写出报告，下一次点击时启动器把它取进 `android/logs/<时间>/android-report.txt`。
- 报告区的扇区与两个镜像不交叉，不靠一次性的真机抽查：每次启动 preinit 都会检查（上文第 2 步，`TestFileMapper.h` 的 `pw3_file_maps_bounds`、`FatCrossLink.h`）。
- 已在真机上验证（2026-11-02）：**同一次启动只写一份，连续两次启动的序号递增 1**。两次点击收走的两份报告各自只有一个 `pw3-android-report-v1 boot=` 头、里面四次采样、末尾 `complete` 和 `kept=97 left_out=0`；序号是 `boot=1793478277`（11-01 21:45 那一程）和 `boot=1793478278`（11-02 06:33 那一程）。状态文件里的 `android=1793478278` 与后一份逐字相同，也就是说收走报告和改写状态是同一次点击里做完的。
- 已在真机上验证（2026-11-02）：**写完报告之后 FAT 干净**。设备回原厂、用户盘挂到电脑上，`fsck_msdos -n /dev/rdisk4s1`（经 `diskutil verifyVolume`，只读，不写任何东西）三个阶段全过、退出码 0：没有交叉链、没有孤立簇、目录项没问题。另一条独立的旁证更直接：`report.bin` 的 mtime 还停在安装器建区的那一刻（设备时间 2026-11-01 04:24），而在那之后已经有两程 Android 往里写过——**写进去了而 mtime 没动，正是"不碰元数据"的意思**。注意这一次用的是 macOS 的 `fsck_msdos`，不是原厂系统里的 `dosfsck`：两者查的是同一套 FAT 一致性，但不是同一个实现。
- 已在真机上验证（2026-11-02）：**报告里记下的版本号就是入口安装的那一版**。报告每次采样都写着 `ro.build.version.incremental=eng.builde.20261031.051622`，而入口 `launcher/release.h` 里的 `build_incremental` 逐字相同——那个串是 `boot/build_launcher.py` 从系统镜像自己读出来的，也正是 `install.c` 用来判断"**这个**入口装的系统编译完了没有"的那一个（`install.c:1578`）。顺带记一笔别去"统一"的地方：同一份镜像里 `ro.build.version.incremental` 是 `eng.builde.20261031.051622`，而 `ro.build.fingerprint` 里那一段是 `builde10310516`，两种写法编的是同一个时刻（10-31 05:16）；安装器用的是前者。
- 尚未在真机上验证：写报告的瞬间断电，重启后 FAT 仍干净、报告区内容要么是旧的要么是新的（64 KB 一次写入不保证原子，所以头部带长度与校验和，读的时候校验不过就当没有）。
- 尚未在真机上验证：preinit 拒绝启动时写报告、下一次点击据此重装这条路径。它只在拒绝启动时才走，要看到它，得先故意把 `android/system.img` 改坏一个字节。

## 启动失败时的出路

### 要解决的问题

开发期间在真机上遇到过一个只有真人用才会碰到的问题：系统镜像有缺陷时，Android 会**反复重启框架**，屏幕一直闪，既进不去桌面，也没有 USB。对一个"只会把数据线插进电脑"的使用者，这看上去等于设备坏了。

### 先把这件事变成"设备自己会出来"

这种状态下 Android 自己的 `RescueParty` 会一路升级到"恢复出厂设置"：那一次 `system_server` 每 14 秒崩一次，18 分钟内走到最后一级 44 次，数据没被清掉纯属侥幸——本机没有 `/misc` 分区、也没有可以进的 recovery，它的重启请求全部失败了。

补丁 `0045`（`ro.rescue_party.no_wipe=true`）把最后一级从"清用户数据"改成"重启"。本机的重启就是离开 Android、回到原厂系统，所以这条路径不再是最后的破坏手段，而是**自动的出路**：

- `RescueParty` 的阈值是"300 秒内 5 次"，每满一次升一级，共四级。上面那种 14 秒一轮的重启循环，约 20 次、不到 5 分钟就会走到第四级。
- 第四级在 `noteBoot()` 里执行，那时 `PowerManagerService` 已经发布但还没 `systemReady`。AOSP 为这种情况留了路：`shutdownOrRebootInternal()` 发现系统还没就绪时，如果 `RescueParty.isAttemptingFactoryReset()` 为真就直接 `lowLevelReboot()`。而 `incrementRescueLevel()` 在执行前就把 `sys.rescue_level` 写成 4，所以这个判断成立，重启立即发生。
- 万一不成立，`executeRescueLevel()` 外面有 `try/catch (Throwable)`，异常只会被记一条日志，不会再害 `system_server` 崩一次——安全网不会变成新的崩溃源。

也就是说：**有了补丁 `0045`，崩溃循环这一类启动失败会在几分钟内自己回到原厂系统。**启动检查失败的两类（存储、接口）也一样，它们自己请求重启（`initcheck/pw3-boot-report.rc`）；入口拒绝启动的那一类由 `PreInit.c` 的 `stop()` 在 120 秒后重启。启动画面上因此写的是"启动失败时 Kindle 通常会自己重启回原来的系统"——**"通常"不是客气话**：不崩溃、也没让任何一项检查失败的卡死，这四条路一条都不覆盖，长按电源键就是为它准备的。

### 先把事实摆清楚

- **本机没有自动的启动循环**。Android 是原厂系统里的书库入口一次性跳进去的；任何重启——包括长按电源键强制复位——都回到原厂系统。没有人点，就不会再进 Android 一次。
- 所以一次失败的代价是"这一次没进去"，不是"设备进不去了"。原厂系统本身就是本机的恢复环境：在那里可以重装、装回旧版本，或者什么都不做继续当 Kindle 用。
- **镜像损坏有专门的检查**：没有校验记录、或镜像文件的大小、修改时间、在 FAT 上的 extents 与记录不符时，preinit 读完整个系统镜像校验 SHA-256；记录对得上时跳过这次全量校验（省下每次启动约 20 秒），改由 Android 起来之后的 `pw3-system-verify` 在后台以最低优先级再读一遍，不符就删掉记录，下一次启动重新全量校验（`preinit/TestFileInit.h`、`SystemStamp.h`、`SystemRecheck.h`）。校验不过时 preinit 停下，把原因写进内核日志和报告区，两分钟后重启回原厂系统，下一次点击据此重装。标记能额外抓到的，只剩"我们自己发的构建有缺陷"。
- 屏幕在闪的时候，任何提示都显示不出来；preinit 也画不了屏。**唯一能被看到的时刻是启动之前。**

### 做法：把出路写在启动画面上

设备多半会自己出来，但使用者得知道那是正常的，而不是又坏了一次；真的卡住（没崩溃，所以 `RescueParty` 不会触发）时也得有一条手动的路。两件事只有启动前能说，就都写在启动画面上。**不按症状分类**：屏幕不动既可能是正常启动，也可能是入口拒绝后那两分钟的等待，使用者分不出来，也不需要分——两种情况的答案是同一个。

| 入口 | 在哪 | 文字 |
|---|---|---|
| 发行版 | `installer/screens/render_screens.py` 的 `BOOT` | 启动时屏幕可能长时间不变，这本身不代表失败，不要强制重启。启动失败时，Kindle 通常会在几分钟内自己重启回原来的系统，书不会丢。没有自己回去，就按住电源键不放，直到屏幕变化（最多约 40 秒），同样回到原来的系统。回到了书库就再点一次：如果是系统文件坏了，这一次会自己查出来并重装，不需要电脑。书和应用数据都在另一个文件里，不会丢。 |
| 发行版（更新后第一次） | 同上的 `BOOT_UPGRADE` | 先说已安装的应用要为新系统重新编译、每个应用大约三到五分钟、不要强制重启；再加一段：启动失败时，Kindle 通常会在几分钟内自己重启回原来的系统，书不会丢。 |
| 宿主机客户端测试 | `boot/launcher/helper.c` 的 `display()` | `ANDROID BOOT 3 MIN. IF STUCK HOLD POWER 20S.` —— 这一程由 `boot/handoff/tests/run_client_test.py` 单独编出来，不带安装器，也不会出现在任何入口里 |

正常情况下这段文字在启动期间留在屏幕上，失败时它就是使用者看到的最后一屏；交接之后那次重画是尽力而为（见下文），所以"最后一屏"不是由代码保证的。

**第一屏不写时长**（2026-10-30，使用者定的）。交接之前画哪一屏是分情况的（`helper.c` 按 `install_upgraded` 在 `BOOT` 和 `BOOT_UPGRADE` 之间选），**交接之后画的一律是通用的 `BOOT`**——`start-picture.h` 里只烘了这一张。而交接之后它要一直留到 Android 的第一帧：普通启动约 3 分钟，换了启动镜像的升级则是每个应用几分钟。任何一个具体时长在两种情况里必有一种是假的，而照着假的那个数去做的使用者，会在编译中途强制重启一台本来正常的机器。

**同样不能写的是"不闪就是正常"**（2026-10-30 Codex 复审查出）。2026-10-30 当天这一屏一度写着"只有屏幕反复闪烁才是没能启动"，而这棵树里就有反例：`PreInit.c` 的 `stop()` 把原因写进报告区之后 `sleep(STOP_SECONDS)`——120 秒——再重启，整个过程**不画任何东西**。入口拒绝启动时，屏幕纹丝不动地停两分钟，然后自己回原厂。把"屏幕不动"说成"在正常启动"，是这个程序自己就能证伪的一句话。所以这一屏既不写时钟也不写症状：使用者真正需要知道的是等待不花代价、而且随时有一条回去的路，这两件事在两种失败里是同一个答案，不必让他先把症状分类。

这一点要靠两处代码才成立。交接之后是新内核的显示驱动，它初始化时无条件清屏、再把自己刚分配的那块缓冲区刷出去，而缓冲区是清零的、零就是黑；不做处理的话，安装器用 eips 画的那一屏活不过驱动加载，屏幕从那一刻起到 Android 首帧是黑的。所以内核在那次刷新前把缓冲区填白（补丁 0403），交接程序加载完驱动就用**同一套排版、同一份字体**把通用的那张 `BOOT` 重新画上去（`boot/handoff-init/make-start-picture.py`，文案与安装器共用 `render_screens.py` 里的常量）。

**这一次重画是尽力而为，不是保证。**有四处它可能不发生，每一处都只写一行内核日志，启动照常往下走（`pw3-handoff-init.c`）：

1. **驱动没加载**——`show_start()` 根本不会被调用（`if (loaded)`）；
2. **`show_start()` 里三条提前返回**——`/dev/fb0` 五秒内没出现、几何尺寸不可用（不是 8 位、或者可见窗口超出映射）、`mmap` 失败；
3. **`refresh()` 失败**——画是写进缓冲区了，但那一次 EPDC 更新没送出去或没等到完成；
4. **整个硬件子进程被跳过或超时杀掉**——它本来就是放在子进程里做时间约束的。

面板上会留下什么，取决于走到哪一条：第 2、3 两类里驱动已经初始化过，内核在那次刷新前把缓冲区填了白（补丁 0403），所以是白屏、没有字；第 1 类驱动压根没初始化，玻璃上多半还是安装器用 eips 画的那一屏。**补丁 0403 保证的是"不黑"，不是"有字"。**所以准确的说法是：正常情况下交接前后都有字，而"整个启动期间屏幕上一直有这段话"没有代码保证它。第 3 类从 2026-10-30 起会在日志里写明 `SCREEN refresh failed` 而不是 `SCREEN up`——在那之前它报的是成功。

画面区域的高度取所有画面里最高的那一屏，由 `render_screens.py` 在构建时算出，放不进状态栏以下、屏幕以内就停止构建；交接程序重画的 `BOOT` 区域是 944×1193（`boot/handoff-init/start-picture.h`）。`installer/install/test_screen.py` 检查 C 代码在设备上拼出的画面与构建时的预览逐像素相同。

### 没有做的：把"上次启动成功了没有"记到盘上

曾考虑再加一个 4 KiB 的小文件，由 preinit 映射成一个 dm 设备，Android 在 `sys.boot_completed=1` 时写入 `ok`，入口脚本下次启动前读它，发现上次是 `attempt` 就先提示、不直接启动。评估后**不做**：

- 它能多拿到的，只有"失败之后再点一次时拦一下"。而设备已经会自己退回原厂系统（`0045`），使用者该做的事（换版本或报告）启动画面上也写了，拦一下并不会改变使用者能做什么。
- 代价不小：已验证启动路径里多一个 dm 映射、`pw3_file_maps` 收据格式变更（`InitCheck` 跟着改）、一个新的 SELinux 域和一个新的开机服务，每次启动都多走一段分支。
- 更要紧的是方向不对：这段代码是安全网，它自己出错就会变成新的启动失败来源——而它要对付的，正是"我们自己的构建有缺陷"。前面那次重启循环的教训是少往启动路径里塞只能上机验证的东西，不是多塞。

如果以后真的出现"同一版本反复失败、使用者分不清状况"的证据，再按上面的设计加也不迟：文件、映射、写入点都已经想清楚了。
