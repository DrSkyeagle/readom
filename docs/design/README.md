# 设计文档

每一份回答一个问题，按"谁带着什么问题来"分的。面向改这套系统的人；装系统的人读 `docs/install.md` 就够了。有英文半边的，文件名里带 `.en`。

| 文档 | 回答什么 | 什么时候读 |
|---|---|---|
| [eink-ui.md](eink-ui.md) | 这块屏幕上的界面按什么规则画 | 改任何会出现在屏幕上的东西之前。代码注释里引它的地方最多，因为数值和理由都在这里 |
| [performance.md](performance.md) | 这台机器的时间和内存花在哪里，各是多少 | 想让某件事变快之前。里面的数都是在装了本系统的 PW3 上实测的，不是估算，也包括"量完发现不值得做"的几项 |
| [app-install.md](app-install.md) | 在这台机器上装一个大应用会发生什么；微信读书怎么自动装 | 改安装路径、改微信读书那条流程之前 |
| [usb-mtp.md](usb-mtp.md) | Android 侧的 USB 文件传输怎么做成的，踩过哪些坑 | 动 USB、adb、MTP 之前 |
| [diagnostics.md](diagnostics.md) | 启动失败时设备自己怎么出来；出了事证据怎么到人手里 | 改启动检查、报告区、日志导出之前 |
| [release-build.md](release-build.md) | 怎么构建一次发行，发行前什么必须为真（含发行清单、密钥、安全复核、会过期的数据） | 发行之前，逐条走 |
| [porting-to-other-models.md](porting-to-other-models.md) | 把这套东西搬到另一台 Kindle 要做什么，哪些是现成的 | 考虑第二个机型时 |

**为什么分成七份**：它们面向不同的读者（改界面的、发行的、移植的）。代码注释里有四十多处"见 design/…"，每处都指向具体的一份，顺着注释找过来的人能直接找到对应内容。反过来，同一件事的两半放在同一份里，例如微信读书的自动安装和"在本机装大应用"、启动失败的出路和诊断通道、安全复核和发行清单，免得读者自己去拼。

**改名或合并时**：仓库里引用这些文件名的地方（包括 `device/` 下的代码注释）必须跟着改，`tools/tests/test_doc_links.py` 会把漏掉的指出来。
