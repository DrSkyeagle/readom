# Which patches have been run on the device

A patch header is written when the patch is, and this series is append-only
(`tools/apply-patch-series.py` records each file's SHA256), so a header cannot be
corrected afterwards: what a patch says about itself is what was known the day it
was written. Ten of the 245 patches of the series end with

> Not run on the device yet when this patch was written.

and nothing used to go back to them. One of the first six -- `aosp-frameworks-base/0008`
-- also stated, in the same voice as its measurements, a premise about what the
device does that nobody had measured. That premise was wrong, it stood for twelve
days, and what it cost was the defect the owner reported four times: tapping an
application turned the screen into the two system bars over nothing for twenty to
thirty seconds.

This file is the thing that goes back. One row per patch that says the sentence
above, and what has happened to it since.
`tools/tests/test_patch_verification.py` fails if a patch says it and has no row
here, or if a row names a patch that does not say it -- so neither a new patch nor
a tidied-up row can leave this list out of date. It looks one level down
(`patches/<series>/NNNN-*.patch`), which is where the series live; the one patch
that sits in `patches/` itself (the bare `timeconst.pl` diff for a host with a
current perl, see `patches/README.md`) is named in the test, so a second patch put
at the top level fails it rather than escaping both checks -- 2026-11-03, found by
counting the files two ways and getting 246 and 245.

**What a row says is not whether the patch is good; it is whether the device has
been asked.** "No" is an acceptable answer as long as it is written down.
