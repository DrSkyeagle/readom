# 补丁系列

Readom 不 fork 上游。内核和 AOSP 的每一处改动都是这里的一个补丁，按项目分目录、按序号排。
这样做的理由是开源这件事本身：读这个仓库的人要能看出"相对 AOSP 8.1_r81 和亚马逊的
Linux 3.0.35，这个项目到底改了什么"，而一棵 fork 回答不了这个问题。

```
projects.txt                    AOSP 项目路径 → 补丁目录，顺序就是应用顺序
0001-timeconst-current-perl.patch  构建宿主机的 perl 太新，内核那个脚本跑不动
android-core/                   内核（Linux 3.0.35，亚马逊 5.16.2.1.1 的 GPL 源码）
test-kernel/                    只给 QEMU 夹具用的那棵内核
aosp-<项目>/                    对应 AOSP 项目的补丁，<项目> 与 projects.txt 对得上
```

`projects.txt` 是**唯一那份名单**：`tools/prepare-aosp-device.sh` 按它的顺序应用，
`tools/export-aosp-images.py` 按它核对每个项目的账本。要加一个新项目，先改它。

## 一条必须知道的规矩：账本只能追加

每棵源码树里有一份 `.pw3-applied-patches.json`（在源码树里，不在这个仓库里），记着已经按序应用了哪些补丁。它**只能追加**：

- 在系列**末尾**加补丁，直接跑应用脚本就行。
- 要改一个已经应用过的补丁，或者在**中间**插一个，账本的前缀就对不上了，脚本会在应用之前拒绝。
  这时**必须重开一棵源码树**，从头按序应用整个系列。2026-10-31 的 `0103` 就是这么来的：
  它要插在 `1053` 之前，于是 85 个补丁重走了一遍。

这不是麻烦，是它该有的样子——"源码树现在是什么状态"必须能从系列本身算出来，而不是靠谁记得
手工打过什么。`tools/verify-tree-matches-series.py` 就是用来核对这件事的（在构建机里跑，
两个参数都是根目录）。

## 写补丁的约定

- 补丁头里写清**为什么**，不只写改了什么。遇到对应的上游提交就引用它的 SHA，并说明是不是同一个改法。
- 内核补丁如果来自上游回移，另写一份 `*-source-provenance.json` 记下出处、核对过的哈希，
  以及本地这一版和上游的差别（比如缩进）。`0103` 旁边那份就是例子。
- 碰 AOSP 的 framework 资源要守两条规矩（**只改值、不加名**；覆盖层条目正上方不写注释），
  理由在 [CONTRIBUTING.md](../CONTRIBUTING.md)。违反第一条会改资源 ID，进而改启动镜像，
  于是使用者升级时 `/data` 里所有应用的机器码全部作废。
- 补丁系列由 `tools/tests/test_patch_series.py` 检查（套件里叫 `patch-series`）：
  编号连续、`projects.txt` 和目录对得上、每个补丁都能干净应用。
